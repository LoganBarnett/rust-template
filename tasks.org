* DONE Reusable CI checks should gate branch pushes, not just pull requests
The reusable workflow's ~changelog~ and ~abi~ jobs both gate on
~github.event_name == 'pull_request'~, so a contributor who pushes directly to a
long-lived branch (or to ~main~ via a non-PR flow) bypasses both the
changelog-entry requirement and the ABI / Upcoming → Breaking gate. CI should
fail the build in those cases too — the asymmetric "ABI break ⇒ Breaking entry"
rule is only useful if it holds on every path into ~main~.

Decide on the right base ref to diff against when the trigger is a ~push~
(probably ~origin/main~ for branch pushes; for pushes to ~main~ itself, either
the previous commit on ~main~ or skip with a clear reason), then drop the
~pull_request~ gate from both jobs in =.github/workflows/reusable-ci.yml=.

* DONE Automate crates.io trusted-publishing setup across the fleet
Setting up trusted publishing on crates.io is a per-crate operation: each crate
must be claimed (initial publish) and then have a publisher config registered at
=https://crates.io/crates/<name>/settings/new-trusted-publisher=.  For a single
project with one crate this is fine; for ~22 projects averaging 3-4 crates each
(60+ configs total) the UI click-through is untenable.

Both halves of the setup are scriptable via a single API token scoped to
=publish-new= and =trusted-publishing= (with crate scope left unrestricted so it
covers every crate the user owns):

- Claiming names: =cargo publish --package <crate>= using the token.
- Registering trust configs: =POST /api/v1/trustpub/github_configs= with body
  =github_config: { krate, repository_owner, repository_name, workflow_filename,
  environment? }=.

Write a helper script (e.g. =trusted-publish-setup.sh= at the repo root, or a
sub-command of an existing tool) that takes a project directory, reads its
workspace crate names from =Cargo.toml=, derives the GitHub =owner/repo= from
the project's git remote, and loops over the crates running both the publish and
the API call.  The token comes from an env var and is never persisted.

Cross-reference: depends on the existing [[*Publish crates for public projects][Publish crates for public projects]] task
for the =publish.yml= workflow the trust configs authorize.

* TODO Reliable launchd reload for Darwin user-agent services

nix-darwin's activation reloads launchd units with the legacy =launchctl load
-w= / =unload= API (=modules/system/launchd.nix=), which is unreliable for *user
agents* on modern macOS: the agent lives in the user's =gui/<uid>= (Aqua)
domain, but activation runs as root, and that domain only exists while the user
is logged into a GUI session.  The net effect is that a deployed plist change
gets written but the running agent is never cycled — it only picks up the change
on the next reboot/login.

Root/system daemons (the =system= domain, addressable directly from the root
activation) are largely unaffected, which is why =nix/lib/mkDarwinService.nix= —
which emits root services — does not hit this.  It surfaced in sytter, which
hand-rolls a =launchd.user.agents= agent: every deploy needed a manual
=launchctl bootout gui/$uid/<label> && launchctl bootstrap gui/$uid <plist>=.

If the template grows a user-agent Darwin service helper (or sytter-style agents
adopt =mkDarwinService=), bake in a =postActivation= reload shim that does the
modern =bootout= + =bootstrap gui/<uid>= dance, guarded on an active GUI session
for the target user.  Leave root/system services on the standard path.

Use the service's configured health endpoint as the liveness signal — the helper
already knows it (it drives the optional healthcheck agent).  After =bootout=,
poll the health URL until it stops answering (service genuinely down) before
=bootstrap=; after =bootstrap=, poll until it returns healthy to confirm the
reload actually landed, and fail the activation loudly if it does not — rather
than fire-and-forget leaving a dead agent (the exact failure mode that hid
sytter's breakage).  Caveats: =Input/output error (5)= is launchd finishing its
domain teardown, which can lag process exit slightly, so still wrap =bootstrap=
in a bounded retry; and when no health URL is configured, fall back to a
TCP-connect (or =launchctl print= state) probe.

The general fix belongs upstream (nix-darwin#1255 "Broken LaunchAgents with
launchctl 2.0"; #1199 "manually removed units not re-added"); the template shim
is the pragmatic local workaround until that lands.

* DONE Reusable publish workflow should create an annotated tag per release
The reusable publish workflow (=reusable-publish.yml=) does version bump →
changelog roll → release commit ("chore: release vX.Y.Z [skip ci]") → cargo
publish, but never creates a git tag.  Downstream consumers lose the
conventional way to refer to a release: =git checkout v0.3.0=, GitHub Releases
binding, =git describe=, and signing/verification tools that expect a tag
object.

Add a tagging step that creates an *annotated* tag — =git tag --annotate
v${VERSION} --message "Release v${VERSION}"= — and pushes it.  Annotated
specifically, not a lightweight tag pointing at the commit object directly: =git
describe= only walks annotated tags by default, GitHub's Releases UI
distinguishes them, and tools that inspect tag metadata read the annotation
payload.

Open design question: tag before or after =cargo publish=?  Tagging first
reserves the version even if the publish fails (which leaves a tag pointing at a
version that never made it to crates.io); tagging after means a brief window
where the crate is live but no tag exists yet.  Pick whichever failure mode is
less bad.

* DONE Reusable publish workflow should skip cargo publish when publish = false
The reusable publish workflow (=reusable-publish.yml=) always runs =cargo
publish= as its final step.  When the target crate is marked =publish = false=
in its =Cargo.toml=, cargo exits 101 with "package.publish must be set to true
or a non-empty list", and the whole workflow run turns red — once per merge to
main, indefinitely, until the consumer flips the flag.

For a downstream project that uses =publish = false= as the "not ready to
publish yet" signal but still wants the version bump → changelog roll → release
commit half of the workflow on every merge, every run is a false alarm. Add a
guard before the publish step that reads =package.publish= for the target crate
and skips =cargo publish= when the crate is not publishable.

Detection is clean via =cargo metadata --format-version 1 --no-deps=: =.publish=
is =null= for default-publishable crates, an empty array =[]= when =publish =
false=, and a list like =["crates-io"]= when restricted to specific registries.
A jq one-liner: not-publishable when =(.packages[] | select(.name == "<crate>")
| .publish) == []=.

The bump/changelog/release-commit steps stay unguarded — that is the whole
point; consumers want the release cadence even before they're ready to publish
to crates.io.

* DONE Darwin services must log to /var/log/<service>/ with rotation
Implemented in =nix/lib/mkDarwinService.nix=: log directory creation lives in
~system.activationScripts.postActivation~, ~StandardOutPath~ /
~StandardErrorPath~ on both the main service and the optional health-check agent
point at =/var/log/<service>/=, and
~environment.etc."newsyslog.d/<service>.conf"~ adds newsyslog rotation rules for
stdout, stderr, and (when enabled) the healthcheck log pair.  Notes preserved
below for future reference and for any new darwin-only services that don't go
through ~mkDarwinService~.

All darwin launchd services should write ~StandardOutPath~ and
~StandardErrorPath~ to ~/var/log/<service>/~ rather than ~/tmp/~ or nowhere.
~/tmp/~ is cleared on reboot and is not where service logs belong. Without
explicit log paths, launchd silently discards all output — making post-mortem
diagnosis impossible.

** Log directory creation

The log directory must exist before launchd starts the agent.  Use an activation
script in the module's ~config~ block:

#+begin_src nix
system.activationScripts.postActivation.text = ''
  mkdir --parents /var/log/<service>
  chmod 755 /var/log/<service>
'';
#+end_src

While not included here, you will also need to ~chown~ the directory if this is
a user service.

** launchd plist

Set both ~StandardOutPath~ and ~StandardErrorPath~ in the agent's
~serviceConfig~:

#+begin_src nix
StandardOutPath = "/var/log/<service>/<service>.log";
StandardErrorPath = "/var/log/<service>/<service>.log";
#+end_src

** Log rotation via newsyslog

macOS ships ~newsyslog~ which reads drop-in configs from ~/etc/newsyslog.d/~.
Add a config via ~environment.etc~:

#+begin_src nix
environment.etc."newsyslog.d/<service>.conf".text = ''
  # logfilename                          mode count size  when flags
  /var/log/<service>/<service>.log        644  5     10240 *    NJ
'';
#+end_src

- ~N~ = no signal (the service isn't syslogd; it re-opens the file on next
  write).
- ~J~ = bzip2 compression for rotated archives.
- ~size~ is in KB (10240 = 10 MB).
- ~count~ is the number of rotated archives to keep.

Adjust ~count~ and ~size~ per service — high-volume services (e.g. Ollama
inference server) need more generous limits than one-shot helpers.

** Reference commit

See =dotfiles= commit =a223015e= (~fix(ollama): add launchd log output with
newsyslog rotation~) for a working example applied to the Ollama darwin module.

* DONE MergeConfig derive macro
Auto-generate the ~CliRaw -> ConfigFileRaw -> Config~ merge from a single type
definition. The ~#[derive(MergeConfig)]~ macro should produce the ~CliRaw~ (clap
Parser), ~ConfigFileRaw~ (serde Deserialize), ~ConfigError~, the
~from_cli_and_file~ resolution function, and the ~CliApp~ trait impl from a
single annotated ~Config~ struct.

** API design

Struct attributes:
- ~app_name = "name"~ — required, used for ~find_config_file~ and
  ~CliApp::app_name~
- ~extra_cli = "Type"~ — optional type flattened into generated ~CliRaw~
- ~extra_file = "Type"~ — optional type flattened into generated ~ConfigFileRaw~

Field attributes:
- ~common~ — log_level / log_format; resolved via ~resolve_log_settings~ against
  ~CommonConfigFile~
- ~env~ — derived env-var name ~<app>_<flag>~ (lowercase, POSIX §8.1)
- ~env = "literal"~ — explicit env-var name (rare; for non-derivable contracts)
- ~name = "field"~ — CLI/file field name (defaults to struct field name)
- ~short = 'x'~ — short flag for clap
- ~default = "expr"~ — default value expression
- ~required~ — error if not provided (no default)
- ~parse~ — CLI/file type is ~String~, parsed via ~FromStr~ to field type
- ~skip~ — not auto-merged; calls ~Config::resolve_<field>(cli, file)~
- ~cli_only~ — not in config file

Generated items:
1. ~CliRaw~ struct (~#[derive(Debug, clap::Parser)]~)
2. ~ConfigFileRaw~ struct (~#[derive(Debug, serde::Deserialize, Default)]~)
3. ~ConfigError~ enum (~File~ + ~Validation~ variants)
4. ~impl Config { pub fn from_cli_and_file(cli: CliRaw) -> Result<Self,
   ConfigError> }~
5. ~impl CliApp for Config~

Example (simple CLI):
#+begin_src rust :exports code
#[derive(Debug, Clone, MergeConfig)]
#[merge_config(app_name = "my-cli")]
pub struct Config {
    #[merge_config(common)]
    pub log_level: LogLevel,
    #[merge_config(common)]
    pub log_format: LogFormat,
    #[merge_config(short = 'n', default = "\"World\".to_string()")]
    pub name: String,
}
#+end_src

Example (server with OIDC):
#+begin_src rust :exports code
#[derive(Debug, Clone, MergeConfig)]
#[merge_config(
    app_name = "my-server",
    extra_cli = "OidcCliFields",
    extra_file = "OidcFileFields",
)]
pub struct Config {
    #[merge_config(common)]
    pub log_level: LogLevel,
    #[merge_config(common)]
    pub log_format: LogFormat,
    #[merge_config(name = "listen", env,
                   default = "\"127.0.0.1:3000\".to_string()", parse)]
    pub listen_address: ListenerAddress,
    #[merge_config(env,
                   default = "std::path::PathBuf::from(\"frontend/public\")")]
    pub frontend_path: std::path::PathBuf,
    #[merge_config(env, required)]
    pub base_url: String,
    #[merge_config(skip)]
    pub oidc: Option<OidcConfig>,
}
#+end_src

* DONE Service helpers should use mkDefault for overridable config
=mkNixosService= and =mkDarwinService= currently assign most of the systemd /
launchd configuration as plain values (=ExecStart=, =Type=, =User=, =Group=,
=Restart=, =RestartSec=, =environment=, =wantedBy=, =after=, =requires=, the
hardening flags, etc.).  Only =WatchdogSec= is wrapped in =lib.mkDefault=.

This forces any downstream module that needs to extend the service — for example
to inject a =--config <generated.toml>= flag into =ExecStart= or add a
project-specific environment variable — to use =lib.mkForce=, which reads as
"I'm fighting the helper" when the intent is just "extend it."  Composition is
the Nix module system's native mechanism for this; the helper should make it the
path of least resistance.

Fix: wrap every value a downstream module might reasonably want to override in
=lib.mkDefault=.  Keep plain assignment only for things that genuinely cannot be
overridden (e.g. the =description= template that hardcodes =${name}=).  Apply
the same change to =mkDarwinService=.

* DONE Document the composition pattern for service helpers
The intent of =mkNixosService= / =mkDarwinService= is that downstream modules
/compose/ with the helper rather than fork it — adding their own

overriding =ExecStart= (or other items, once mkDefault is in place) when the

Without a worked example, spawned projects either re-implement their own

* DONE Pre-commit hook skips renamed files
The hook collects staged files with =git diff --staged --name-only
--diff-filter=ACM=, which filters to *A*dded / *C*opied / *M*odified and
silently excludes *R*enamed.  When =git mv= is followed by edits to the renamed
file's content (the common case), git classifies the staged change as =R= rather
than =M=, so the path never lands in =STAGED_FILES=.  treefmt is then invoked
without that file, the re-stage loop skips it, and the commit captures whatever
pre-format content the rename left behind.  The working tree later shows a diff
against HEAD once anything else triggers treefmt over the affected file, which
reads as "files get modified after the commit" — the artifact that surfaced
this.

Fix: change the filter to =ACMR= so renames are included.  Verify by staging a
=git mv= + content edit and confirming the post-commit working tree matches
HEAD.

Landed in v0.19.0: the function ships in =nix/lib/mkDarwinCrossPackages.nix=,

Cross-compile the darwin release binaries on Linux runners instead of GitHub's
scarce, slow macOS runners (a free-tier =x86_64-darwin= job sat queued for
hours, never producing an artifact).  The whole approach was proven end to end
with a throwaway probe (=~/dev/darwin-cross-probe=); this entry records the
recipe so it can become a real foundation-lib function.  The probe cross-built,
on Linux builders, three running signed Mach-O =aarch64-apple-darwin= binaries:
=hello= and the repo's own =compliance-cli= (libSystem-only, on a Raspberry Pi),
and =sonify-health='s cli (=cpal= -> CoreAudio/AudioToolbox, on an x86_64-linux
box).  All three ran natively on Apple Silicon.

** Design: a third ~mk*Packages~ sibling

~mkDarwinCrossPackages~ sits beside ~mkRustPackages~ (native) and
~mkMuslPackages~ (static-musl variant), and follows the same shape: it yields
outputs only when the build platform is Linux and returns an empty set
otherwise.  The release-binaries CI matrix's darwin rows then move from macOS
runners building =.#packages.<darwin>.<crate>= natively to Linux runners
building the cross attr.  The native darwin path stays for Mac-local dev and as
a reproducibility oracle; it just leaves the artifact-production critical path.

** The proven recipe

- Build platform is =x86_64-linux= specifically — not "any Linux".  The
  =apple-sdk= deps fail to build on =aarch64-linux= (=libsbuf= meson breakage);
  =x86_64-linux= is also what GitHub CI provides.  (libSystem-only crates do
  cross fine on =aarch64-linux= — the Pi proved it — but the framework SDK does
  not, so standardise on =x86_64-linux=.)
- Codegen: rustc with the =aarch64-apple-darwin= target added via rust-overlay
  (=rust-bin...override { targets = [...]; }=), exactly as ~mkMuslPackages~ adds
  the musl target.
- Linker: =zig= via =cargo-zigbuild=.  This is the crux — nixpkgs' native cross
  stdenv is blocked because =cctools= (Apple's =ld64=) is darwin-gated
  (=meta.platforms= excludes Linux); zig ships its own Mach-O linker that runs
  on Linux and sidesteps it entirely.
- Startup/runtime glue and ad-hoc code signing come free from zig — the linked
  binaries carry =flags=0x20002(adhoc,linker-signed)=, which is what lets an
  arm64 Mach-O execute at all.  No =codesign= / =rcodesign= step needed.
- libSystem-only crates need *no* Apple SDK: zig bundles the libSystem stubs.
  This is the clean, license-free path and should be the default.
- Framework crates need Apple's interface data — headers (for any bindgen) and
  =.tbd= link stubs.  Crucially this is *inert fetched data*, available as
  =pkgs.apple-sdk.src= (a plain =fetchurl= of =MacOSX<ver>.sdk=).  The full
  =apple-sdk= package does *not* build on Linux (its =Csu= component shells out
  to =clang=, absent on a gcc stdenv), but we never need the assembled package —
  only its =.src=, which realises on Linux as a copy-not-compile step and
  carries the CoreAudio/AudioToolbox frameworks.  So consume =apple-sdk.src=
  directly; do not fight the wrapper.
- zig's Mach-O linker does not derive the framework search path from
  =-isysroot=, so the framework path must be handed to the linker explicitly,
  target-scoped so host proc-macro links keep the native linker:
  =CARGO_TARGET_AARCH64_APPLE_DARWIN_RUSTFLAGS= =
  ="-Clink-arg=-F${sdk}/System/Library/Frameworks -Clink-arg=-L${sdk}/usr/lib"=.
- Dep vendoring via crane's ~vendorCargoDeps~ so the build runs offline in the
  sandbox (the git =orgize= dep vendored cleanly this way).

** The SDK is passed as a derivation, not a boolean

~mkDarwinCrossPackages~ takes a per-call ~appleSdk~ argument that is the SDK
*derivation* (default ~null~), not a flag.  When it is set the function wires
=SDKROOT= + the framework search path; when it is null the build is pure zig
with no SDK — the clean, licence-free path for projects whose executables only
hit libSystem (the =cli= archetype, =compliance-cli=, most tools).  Passing a
derivation rather than a boolean avoids special-casing, and leaves room to one
day pass a pinned version (=apple-sdk_15.src=) or a non-nixpkgs SDK.

Rejected the boolean (and the Cargo.lock auto-detect) deliberately: the SDK is
genuinely not free, so it cannot be always-on (that would force =allowUnfree=
fleet-wide), and auto-detecting "does a crate link frameworks" is too much magic
for something this consequential — the framework need lives only in the crates'
build-time link directives, with no Nix-level marker (it is implicit in the
native darwin stdenv), so any auto-detect would be a heuristic lockfile scan.

The cross-build itself is *always on* — it is strictly better than macOS runners
and free for libSystem executables, so the template-emitted =flake.nix= always
calls ~mkDarwinCrossPackages~ (beside ~mkMuslPackages~), with no =appleSdk=.  A
project that links Apple frameworks (anything pulling =cpal=, =objc2-*=,
=core-foundation=, =security-framework=, =coreaudio-sys=, …) — and note this is
not CLI-specific; the =server= crate links them just as readily — touches two
visible spots in its own =flake.nix=:
1. its nixpkgs import gains =config.allowUnfree = true= and
   =config.allowUnsupportedSystem = true= (the latter whenever that =pkgs= is
   non-darwin, i.e. Linux CI), because =apple-sdk= is unfree and darwin-gated;
2. it passes =appleSdk = pkgs.apple-sdk.src= to the already-present
   ~mkDarwinCrossPackages~ call.  Keeping the unfree acceptance in the spawn's
   own =pkgs= config is a feature: the licence consent is visible in the spawn's
   file, not smuggled into a foundation boolean.  =apple-sdk.src= is a
   =fetchurl= (content-addressed, platform- independent output), so the
   consumer's =pkgs.apple-sdk.src= realises fine on the x86_64-linux builder
   regardless of which =pkgs= it came from.  The matrix wiring lives in
   =.github/workflows/reusable-release-binaries.yml= once implemented.

** Implementation steps

* TODO Mark internal-only commits so they do not cut a release
Every push to =main= cuts a release: a minor version bump, a crates.io publish,
and a release-binaries build.  Some commits produce *no outward-facing change* —
the build output is byte-for-byte identical to the prior release.  Adding an
internal test crate (the =darwin-cross-probe= idea), flipping a =tasks.org= TODO
to DONE, or an internal-only documentation edit all fall here.  Cutting a full
release for these — a new crates.io version nobody needs, a fresh binary build —
is waste.  We want a way to mark such a commit as internal-only so the publish
pipeline skips the version bump / publish / binary build (or skips the release
entirely).

Design notes:
- The honest test is *artifact byte-identity*, not "it's only docs".  This ties
  to the reproducibility thread from the build-provenance work: a reproducible
  build lets the pipeline /verify/ the claim (rebuild the prior release's
  artifact and diff) rather than trust a label.  A weaker first cut is a
  path-based guard — the commit touches nothing under the artifact-affecting
  paths (=crates/=, =Cargo.*=, build inputs) — but the binary-match check is the
  real guarantee.
- Not all documentation is internal-only.  =CONTRIBUTING.org=, =tasks.org=, and
  =README.org= never ship, so they qualify; but anything that lands /in/ the
  distributed artifact does not — e.g. man pages once we ship them (see the
  man-page task below), or embedded help text.  The marker must key on "does the
  artifact change", not "is this a doc".
- An internal-only commit also has no changelog entry (nothing user-facing),
  which currently trips the =changelog-required= CI gate.  The same marker
  should exempt it from that gate — the principled resolution of the tension
  where a docs-only or internal PR is forced to invent a changelog entry.
- Open questions: how the marker is expressed (a commit trailer, a PR label, a
  =rust-template.json= flag?), how =publish.yml= detects it, and whether it
  skips the whole release or only the version bump + publish while still
  attaching binaries.

How much Nix already gives us, and what blocks the rest:
- Nix store paths are content-addressed by their inputs, so a branch build
  pushed to a shared binary cache /is/ the "store it somewhere" mechanism, and
  main building the same tree is a cache *substitution*, not a rebuild.  "Flip a
  bit to release" becomes "the publish job uploads the already-built store
  path".  So the substrate exists; we are not starting from zero.
- The specific thing that breaks byte-identity in our pipeline is the
  version-bump release commit: the branch builds at the pre-bump version, the
  release rewrites =Cargo.toml= and rebuilds, and cargo bakes
  =CARGO_PKG_VERSION= into the binary — so the released artifact genuinely
  differs from what the branch built.  Injecting the version at publish time
  instead of committing it into =Cargo.toml= would make the branch artifact
  bit-identical to the release, but that is an invasive change to how versioning
  works.
- GitHub's other two walls: a merge creates a new commit (a fast-forward or
  squash keeps the tree content identical, so the Nix source hash matches; the
  =[skip ci]= bump commit does not), and Actions has no native "promote a
  previously-built artifact" verb.  Operator flagged this is probably not fully
  achievable without fighting Actions, so this is a direction/someday, not a
  committed plan.
- DONE — near-term stepping stone: PR CI now builds every x86_64-producible
  release artifact (the =release-artifacts= job in =ci.yml=), so a branch proves
  the artifacts build even though =main= still rebuilds them.  The rest of this
  entry (the predictive RC-branch promote) remains the open work.

Refinement — the predictive "release-candidate" branch.  Rather than relying on
a persistent Nix cache (which needs private infrastructure, with the attendant
trust and operational cost), exploit that our versioning is /predictable/ (next
= minor + 1).  After a PR's checks pass, spin a release-candidate branch off it
that does the whole release prep speculatively: "if this merged now it would be
=v0.19.0=", so bump =Cargo.toml=/=Cargo.lock=, roll the changelog, tag, and
build the =v0.19.0= artifacts — the exact bytes main would produce.  This
dissolves the version-bump byte-identity problem above, because the artifact is
built /at/ the post-bump version, not before it.  Merge then degenerates to a
promote:
- The binaries persist with no private cache — attach them to a *draft* GitHub
  release; merging publishes the draft.  crates.io can be upload-not-rebuild
  too: =cargo package= produces the exact =.crate= on the RC branch, and the
  publish step just uploads that file.
- Main does almost nothing: fast-forward to the RC tip (the bump, changelog, and
  tag commits already exist there, so no =[skip ci]= commit is needed), publish
  the draft release, upload the prebuilt =.crate=.  No rebuild.
- The version prediction is only valid against the actual =main= tip, so two PRs
  that both predict =v0.19.0= would collide.  Two ways to serialize:
  - A formal GitHub merge queue.
  - Lighter, and preferred here: an invalidate-and-regenerate loop.  When A
    merges, delete every other open PR's now-stale RC branch (B predicted
    =v0.19.0=, which is taken).  B must rebase onto the new =main= anyway — that
    required rebase is the trigger to regenerate B's RC, now predicting
    =v0.20.0=.  So the RC generation is uniform: "after a PR's checks pass on
    any push (including a rebase), build its RC at the current predicted
    version", plus "on merge, drop the other PRs' RCs."  The only waste is the
    loser's speculative build, thrown away and rebuilt on rebase.  For this
    fleet that churn is rare: human PRs are effectively one-at-a-time, and
    dependabot PRs go through the same RC flow but do not pile up because the
    existing dependabot auto-merge drains them serially as each goes green — so
    the invalidate-and-regenerate loop just runs automatically as they clear,
    rather than accumulating into a parallel backlog.  That is why the lighter
    loop beats standing up a merge queue.

* TODO Enforce linear history on spawns' main branch
Give spawns the merge philosophy (no merge commits on =main=) through the
branch-protection-as-code mechanism the template already ships.  GitHub has no
native repo-root file for these settings — the =.github/settings.yml= people
reach for belongs to a third-party app (Probot "Settings"), not GitHub itself —
but =reusable-branch-protection.yml= already =PUT=s
=template/.github/branch-protection.json= to the branch-protection API on
change, which is our self-contained equivalent.

- Add =required_linear_history: true= to the template's
  =.github/branch-protection.json=.  This forbids merge commits on =main=,
  forcing squash or rebase-and-merge — the enforceable equivalent of ff-only.
  (A literal git fast-forward is not a GitHub merge button; it always mints new
  commit objects — even rebase-and-merge rewrites SHAs — so linear history is as
  close as the platform gets.)
- Optional, to remove the "Create a merge commit" button entirely: set
  =allow_merge_commit: false= via the repo-settings endpoint (=PATCH
  /repos/{owner}/{repo}=) — a different API than branch protection, which the
  same workflow could also call.
- Tie-in: =required_linear_history= is a prerequisite for the release-candidate
  promote vision above — "fast-forward =main= to the RC tip" only works on a
  linear-history branch.

* TODO Refine the rustfmt.toml byte-match into value checks
=rustfmt.toml= is currently guarded by =file-matches-template= (byte-for-byte
equality with the template).  That is the blunt stopgap the "Choosing a check
kind" guidance in =docs/compliance.org= warns against: it forbids a spawn from
adding its own rustfmt settings, even though that is a legitimate additive
deviation.  Replace it with value checks (=toml-path-equals=) on the settings
that actually matter — the ones the template means to keep in lockstep — so a
spawn can extend the file without tripping compliance.  Same shape as the
=treefmt= checks, which already assert wiring is present rather than demanding
an exact file.  Audit the other =file-matches-template= uses (if any) the same
way; the goal is that nothing relies on byte-equality unless an exact match is
genuinely required, which may be nowhere.
