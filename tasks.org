* DONE Land Windows cross-compilation as two coordinated PRs

The Windows cross-compilation work — native gnullvm binaries for x86_64 and
aarch64, an opt-in MSVC path, a wine smoke test, the server crate's
Windows-portability, and the regression-fixture guards (see the two DONE entries
below for the technical detail) — is complete and validated locally, but it
lands as *two* pull requests rather than one.

The reason is a provider/consumer ordering constraint.  The emitted project's
~flake.nix~ references foundation library functions (~mkWindowsCrossPackages~,
~mkWindowsMsvcCrossPackages~, ~xwinSdk~, and the wine-smoke helper) that must
exist in a *published* foundation.  If the emitted flake references functions
that live only on a feature branch, a spawn's flake fails to evaluate against
~main~ until that branch merges — so the provider and the consumer cannot ship
in a single PR.

** PR A — provider (branch ~windows-cross-foundation~)

Adds the cross-compilation helpers to ~foundation.lib~, makes the foundation
crate itself Windows-portable (the systemd integration is gated to Unix, with a
no-op stub for every other target), dogfoods the Windows builds on this repo's
own binaries, extends ~crates/cross-fixture~ to compile the whole server shape
for the Windows targets as a regression guard, and teaches the stale-literal
compliance check to accept the manifest's own filename.  It is self-contained
and passes CI on its own — it never touches the emitted template, so a spawn
built against it behaves exactly as before.  This merges and *publishes a new
foundation version* first.

** PR B — consumer (branch ~windows-cross-template~, based on A)

Wires the now-published helpers into ~template/flake.nix~ so a spawn
cross-compiles its own binaries for Windows, adds the Windows release-binary
rows (with the MSVC ones gated on a per-project manifest flag), and fixes the
spawn regressions the wiring surfaced — a mangled manifest-filename reference
that broke every spawn's flake evaluation, and a stray-literal assertion (also
made fork-owner-agnostic while there).  It is opened only *after* PR A merges
and its foundation version is published, so the emitted flake resolves those
functions from a released foundation rather than an unpublished branch.

** Landing notes

- Order: PR A → publish foundation → PR B.  Flip this entry to DONE once B

- Both branches are rebased onto current ~main~.  The one non-trivial conflict
  was ~main~'s ~sd-notify~ 0.4 → 0.5 upgrade, reconciled by keeping the new API

- PR B adds Windows rows to the *shared* reusable release workflow, which

- The original branch ~compliance-embedded-frontend-checks~ is kept as the

  its original series of commits and squashed to a single commit locally — on

* TODO Emit spawns with a complete, self-consistent Cargo.lock

A freshly spawned project cannot ~nix build~ its server until its ~Cargo.lock~
is regenerated by hand: ~new-project.sh~ / ~crate-add.sh~ add crates (and their
dependencies, e.g. ~rust-embed~) to ~Cargo.toml~ but never regenerate the lock,
and the copied ~template/Cargo.lock~ is itself stale — it predates the
frontend-embed work and is missing ~rust-embed~ entirely.  crane builds from the
committed lock offline, so the mismatch fails the build with "no matching
package named ...".

This is *not* a propagate-foundation-lock-to-spawns problem (that is the
compliance-sync domain; each spawn is its own repo with its own Dependabot).
The fixes belong at emission time:

- ~new-project.sh~ should run ~cargo generate-lockfile~ in the dev shell after
  ~crate-add~ settles the crate set, so every spawn is born with a lock matching
  its *actual* crates (a subset spawn omits a crate, so just fixing
  ~template/Cargo.lock~ is not sufficient on its own).
- A drift guard — a template-CI or compliance check that fails when
  ~template/Cargo.lock~ falls out of sync with ~template/Cargo.toml~ — so the
  template's own lock cannot silently rot again the way it did after the
  frontend-embed commit.

Surfaced while validating the server's Windows cross-build (which needs a
complete lock to resolve ~rust-embed~).

* DONE Cross-compile native Windows binaries for x86_64 and aarch64

Releases built for the mainstream Unix-like targets but not Windows.  Windows is
now built too, for both =x86_64= and =aarch64=, cross-compiled on a Linux runner
(and on a contributor's Mac) so a release never waits on a Windows runner.

The zig pipeline that cross-compiles macOS does not extend to Windows —
~cargo-zigbuild~ supports only Linux and macOS targets, and zig's lld emits the
MSVC import-library format rather than MinGW's.  The build instead targets the
~*-pc-windows-gnullvm~ triples (Tier 2 with host tools since Rust 1.91) and
links with ~llvm-mingw~, which — unlike GCC-mingw — covers both Windows
architectures from one toolchain.  The result is a native Windows PE that runs
on stock Windows with no Cygwin/MSYS2 layer; a pure-Rust binary depends only on
the OS Universal CRT.

Key decisions:
- ~nix/lib/llvm-mingw.nix~ vendors mstorsjo's prebuilt toolchain as a
  fixed-output derivation (per build host: Linux ELF via ~autoPatchelfHook~,
  macOS universal Mach-O as-is), so nothing leaves the Nix model and no Docker
  is involved.
- ~nix/lib/mkWindowsCrossPackages.nix~ mirrors ~mkDarwinCrossPackages~ but is
  *host-agnostic* (no ~x86_64-linux~ gate — llvm-mingw ships a per-host
  toolchain) and does no signing (Windows loads unsigned PEs).  llvm-mingw's
  clang wrapper is both linker and C compiler, so a C-compiling dependency
  (~ring~, a ~*-sys~ crate) builds in crane's deps-only phase, exactly as the
  darwin/gnu-portable helpers route CC/CXX through zig.
- To keep it from regressing, =crates/cross-fixture= gained a ~cfg(target_os =
  "windows")~ arm — a windows-gated ~ring~ (the C toolchain) and a ~winmm~
  import-library link (a non-default system DLL) — built by the root flake as
  =cross-fixture-{x86_64,aarch64}-windows= on every PR.  See the
  "mkDarwinCrossPackages fails for workspaces with C-compiling deps" entry for
  the pattern this follows.
- The x86_64 binary is smoke-tested under ~wine~ (the ~windowsSmoke~ flake
  check, gated to ~x86_64-linux~); aarch64 is build-verified only, since no
  arm64-Windows runner exists and wine cannot execute an arm64 PE.
- Release assets ship as =.zip= (with the =.exe= inside), the format Windows
  users expect; other targets stay =.tar.gz=.  ~zip~ was added to the CI shell.

The default path links no Microsoft code (gnullvm uses LLVM's runtime plus the
OS UCRT), so there is no SDK licence to accept.  See the MSVC opt-in follow-up.

* DONE Add a Windows MSVC (xwin) opt-in cross path

The default Windows build targets gnullvm (see the entry above), which covers
pure Rust and any dependency whose C builds with llvm-mingw.  A dependency that
*requires* the MSVC ABI (a prebuilt MSVC-only library, MSVC intrinsics) needs
the ~x86_64-pc-windows-msvc~ target instead.  It is now built when a project
opts in with ~"windows-msvc": true~ in ~rust-template.json~ — one flag that both
hands the emitted ~flake.nix~ the SDK and adds the release-binary row in CI.  It
is x86_64-only: on ~aarch64-pc-windows-msvc~ the ~cc~ crate drives clang in GNU
rather than clang-cl mode and any C-compiling dependency fails, and arm64
Windows is already fully served by the gnullvm default.

Key decisions:
- ~nix/lib/xwin-sdk.nix~ splats Microsoft's CRT/SDK with ~xwin~ as a
  fixed-output derivation, so the sandboxed build stays offline with no Docker.
  ~--accept-license~ lives here, so evaluating it — which turning the flag on
  does — accepts Microsoft's licence in the consumer's own project, mirroring
  how ~appleSdk~/~allowUnfree~ is surfaced for the darwin cross build.
- ~--disable-symlinks~ plus lowercasing the import-library filenames makes the
  splat tree byte-identical on every build host (one output hash, and it builds
  on a case-insensitive macOS filesystem where xwin's case-fix symlinks cannot),
  while still resolving the SDK's mixed-case names at link time.
- ~nix/lib/mkWindowsMsvcCrossPackages.nix~ takes the crane-native offline route
  rather than invoking ~cargo xwin~ (which would download at build time): it
  sets the linker (~lld-link~), compiler (~clang-cl~), and archiver (~llvm-lib~)
  directly against the pre-fetched SDK.  ~xwinSdk~ is an ~appleSdk~-style opt-in
  parameter — null builds nothing.  Host-agnostic and no code signing, like the
  gnullvm helper.
- The root flake dogfoods the opt-in (compliance-cli and the cross-fixture,
  which exercises the ~ring~ C toolchain through clang-cl); the reusable release
  workflow resolves the target set from the flag so opted-out spawns fetch no
  Microsoft SDK.

Licensing is a non-issue for a normal public binary: dynamic-CRT MSVC (the
default) redistributes nothing — the UCRT is an OS component on Windows 10+ —
and the only genuine edge, a copyleft app statically linking the MSVC CRT, is
avoided by the gnullvm default anyway.

* DONE Embed the Elm frontend into the server binary

Release binaries shipped as a bare executable, but the server served its
frontend from a directory on disk (~--frontend-path~, defaulting to
~frontend/public~ and pointed by the NixOS/Darwin modules at a ~share/~ symlink
in the Nix store).  A downloaded release binary therefore had no frontend at
all: the compiled Elm bundle never travelled with the artifact.

The fix embeds the bundle into the binary via ~rust_embed~ so a release is
atomically self-contained — one file, nothing to ship alongside it.  The
foundation's SPA service became generic over a ~RustEmbed~ type and is installed
with a new ~Server::spa::<Frontend>()~ builder; the ~frontend_path~ field was
removed from ~ServerRunConfig~ / ~BaseServerState~ and the ~--frontend-path~
flag and ~frontendPath~ NixOS option were dropped.  The application crate
declares the ~Frontend~ embed type; a ~build.rs~ resolves the asset directory
(defaulting to the in-tree ~frontend/public~) and exports it as
~RUST_TEMPLATE_FRONTEND_DIR~ for the ~#[folder]~ attribute.

Key decisions:
- ~rust_embed~ reads assets from disk in debug builds and embeds them in release
  builds, so a downloaded release is self-contained while ~cargo run~ still
  picks up ~elm make~ output without recompiling the server.  Addressed the
  concern that embedding bloats memory: assets live in a demand-paged read-only
  data section, so they are not resident until touched and do not affect
  codegen.
- The ~#[folder = "$RUST_TEMPLATE_FRONTEND_DIR"]~ interpolation requires
  ~rust_embed~'s ~interpolate-folder-path~ feature; without it the ~$VAR~ is
  taken literally.  ~mime-guess~ supplies the ~Content-Type~ the SPA service
  returns.
- ~template/nix/packages/server.nix~ passes the freshly compiled Elm derivation
  through ~RUST_TEMPLATE_FRONTEND_DIR~ to the crane build.  Because every
  release variant (native, musl, gnu-portable, darwin-cross) resolves the server
  crate through the same ~nix/packages/server.nix~ per-crate override, the one
  change embeds the bundle in all of them with no per-builder edits.

* DONE Migrate CI off the deprecated Magic Nix Cache

Determinate shut the free ~magic-nix-cache~ backend down in February 2025; the
reverse-engineered revival throttles against GitHub's cache API with the ~HTTP
418~ crashes noted under the darwin-cross task below.  Replace the
~DeterminateSystems/nix-installer-action~ + ~magic-nix-cache-action~ pair across
all CI workflows with ~nixbuild/nix-quick-install-action~ +
~nix-community/cache-nix-action~, which caches ~/nix~ in the GitHub Actions
cache with no external service or signing key (the property of Magic Nix Cache
worth keeping) and benchmarks fastest of the available options.

Done on branch ~nix-cache-migration~.  The installer + cache pair is factored
into a single composite action, ~.github/actions/setup-nix~, so the versions,
~nix_conf~, cache key, and rationale live in one place and a version bump is a
one-line edit rather than an 11-site sweep.  The 11 call sites reference it two
ways, both deliberate:
- ~ci.yml~ (rust-template's own, non-reusable workflow) uses the local
  ~./.github/actions/setup-nix~ ref, so a PR editing the action is tested
  against the PR's own copy — same reasoning as its local ~reusable-ci.yml~ ref.
- The ~reusable-*.yml~ workflows use the full
  ~LoganBarnett/rust-template/.github/actions/setup-nix@main~ ref: a ~./~ ref
  inside a reusable workflow resolves against the *caller's* checkout (the
  spawned project), which does not have the file.  The cost is that these jobs
  pin the action to ~@main~ rather than the PR SHA; it is still smoke-tested on
  the PR SHA by ~ci.yml~'s own jobs above, so a breaking edit is caught.

Key decisions captured in the action / workflow comments:
- ~nix_conf~ sets ~experimental-features = nix-command flakes~ explicitly —
  ~nix-quick-install-action~ writes the supplied conf verbatim and, unlike the
  Determinate installer, does not enable flakes by default.
- ~keep-outputs~/~keep-env-derivations~ so the ~nix develop~ devShell closure is
  retained as GC roots and actually lands in the cached tarball.
- Cache key includes ~runner.arch~ (the release-binaries matrix spans x86_64 and
  aarch64 Linux runners, which must not share a store cache).
- ~gc-max-store-size-linux: 5G~ (set once in the action) bounds the saved
  tarball on the light jobs.
- The 3 heavy cross-compile jobs (~release-artifacts~, the release-binaries
  ~build~ matrix, and the ~darwin-cross-fixture~) pass the action's ~save-store:
  "false"~ input to run restore-only, so their large musl/zig-cross-darwin
  closures do not bloat and LRU-evict the shared 10 GB toolchain cache the light
  jobs depend on.
- No ~purge~: it needs ~actions: write~ in every consumer, and GitHub's own 10
  GB LRU eviction retires stale keys, so omitting it keeps these reusable
  workflows drop-in for spawned projects.

Shipped as two PRs, because the composite action's ~@main~ references cannot
resolve until the action itself is on main: #8 (~v0.23.0~) landed
~.github/actions/setup-nix~ on its own, then #7 wired every workflow to it and
went fully green — the reusable-workflow jobs that had failed with "Can't find
'action.yml' ... @main" now resolve it.  The green run proves resolution and
correctness; the cache hit-rate win (and that the 5G bound plus restore-only
heavy jobs keep the repo under GitHub's 10 GB cap) is only observable across
subsequent runs once #7 is on main.  If the cross closures later prove worth
caching, give the heavy jobs a dedicated key rather than re-enabling ~save~ on
the shared one.

* DONE mkDarwinCrossPackages fails for workspaces with C-compiling deps
Fixed by setting the ~cc~-crate cross vars ~CC_<triple>~ / ~CXX_<triple>~ (the
underscored target triple, e.g. ~CC_aarch64_apple_darwin~) in ~darwinArgs~ to
~zig cc~ / ~zig c++~ wrapper scripts, so every cargo phase — including crane's
deps-only ~cargo check~ — compiles C through zig, not just the final ~cargo
zigbuild~.  The wrappers mirror the ones ~cargo-zigbuild~ writes internally
(~cargo-zigbuild zig cc -- -g -fno-sanitize=all -target <arch>-macos-none~), and
it honours ours because it only sets its own when the var is unset
(~add_env_if_missing~).  ~SDKROOT~ from ~sdkEnv~ is picked up by the ~zig cc~
shim for framework builds; a libSystem-only crate like ~ring~ needs no SDK.

Two corrections to the diagnosis below: ~cargo-zigbuild~ /does/ have a ~check~
subcommand, but the env-var route is preferable because it is
invocation-independent (covers check, deps-only, build, and any future phase
uniformly).  ~AR~ / ~RANLIB~ were left on the host tools, matching
~cargo-zigbuild~'s own default — only C /compilation/ was failing, not
archiving.

Validated by temporarily adding ~ring~ to =crates/compliance-cli= and building
~.#packages.x86_64-linux.compliance-cli-aarch64-darwin~ on the Linux builder: it
produced a clean arm64 Mach-O with no ~gcc: … '-arch'~ errors and the
~cargo-package-deps~ derivation built successfully.

To keep it from regressing, a permanent guard was added: =crates/cross-fixture=,
a build-only crate (never published or released) that carries a macos-gated
~ring~ dependency (the C path) and links ~CoreFoundation~ (the framework/SDK
path).  The root =flake.nix= cross-builds it with =apple-sdk.src= via an
unfree-accepting pkgs, and a =Darwin cross fixture build= CI job builds both
=cross-fixture-<arch>-darwin= attrs on every PR, so a future break in either
path fails the build.  The escape happened because the template's own crates are
pure Rust with no C or framework deps, so CI only ever exercised the happy path;
the fixture supplies the missing consumer-workspace shapes.

The macOS-cross release build (=nix/lib/mkDarwinCrossPackages.nix=) fails for
any workspace whose dependency tree compiles C or assembly in a build script —
e.g.  ~ring~ (pulled in by a rustls TLS stack).  The pure-Rust cross-compile is
fine; only the C portions break, because they are compiled with the host ~gcc~
instead of ~zig cc~.

** Symptom
First observed in sonify-health (PR #11, Actions run 28544803071, job "Release
artifacts build"):

#+begin_src text :exports code
building '/nix/store/…-cargo-package-deps-0.1.0.drv'...
error: Cannot build '/nix/store/…-cargo-package-deps-0.1.0.drv'.
       Reason: builder failed with exit code 101.
       >   cargo:warning=gcc: error: unrecognized debug output level 'full'
       >   cargo:warning=gcc: error: unrecognized command-line option '-arch'
       >   cargo:warning=gcc: error: unrecognized command-line option '-mmacosx-version-min=10.7'
error: Cannot build '…-sonify-health-cli-0.1.0.drv'.    Reason: 1 dependency failed.
error: Cannot build '…-sonify-health-server-0.1.0.drv'. Reason: 1 dependency failed.
#+end_src

~-arch~, ~-mmacosx-version-min=…~, and ~-g full~ are Apple/clang flags the ~cc~
crate emits when ~TARGET=*-apple-darwin~.  The host ~gcc~ rejects them and the
build script aborts.

** Root cause
~darwinArgs~ swaps only the build command to zig:

#+begin_src nix :exports code
cargoBuildCommand = "cargo zigbuild --release";
CARGO_BUILD_TARGET = target; # aarch64-apple-darwin / x86_64-apple-darwin
#+end_src

~cargo-zigbuild~ sets the ~cc~-crate cross env (~CC_<target>=zig cc …~) only for
that one wrapped invocation.  But crane runs other cargo invocations that also
execute build scripts — notably the shared deps build
(=nix/lib/mkRustPackages.nix=, ~cargoArtifacts = craneLib.buildDepsOnly
commonArgs~), which runs crane's default ~cargoCheckCommand~ (plain ~cargo
check~, not zigbuild).  During those, ~ring~'s build script calls the ~cc~ crate
for the darwin target with ~CC_<target>~ unset, so it falls back to the host
~gcc~ with Apple flags → failure.  The zig CC override is scoped to ~cargo
zigbuild~; the C-compiling build scripts that run under ~cargo check~ /
deps-only are not covered.

** Fix direction
Make the darwin-target C toolchain env explicit and invocation-independent
rather than relying on ~cargo zigbuild~ to set it.  In ~darwinArgs~, set the
~cc~-crate cross vars to zig-based wrappers so every cargo phase (check,
deps-only, build) compiles C through zig:

- ~CC_<target>~, ~CXX_<target>~, and likely ~AR_<target>~ pointed at ~zig cc~ /
  ~zig c++~ / ~zig ar~ wrapper scripts targeting ~aarch64-macos~ /
  ~x86_64-macos~, reusing the existing ~SDKROOT~ / framework paths from
  ~sdkEnv~.
- Confirm ~CARGO_TARGET_<TARGET>_LINKER~ still points at the zig linker for the
  final link.
- Overriding ~cargoCheckCommand~ to zig is not viable — ~cargo-zigbuild~ has no
  ~check~ subcommand — so set the env vars directly.  ~cargo-zigbuild~ builds
  equivalent wrappers internally; the task is exposing them to crane's
  non-zigbuild phases.

** Reproduce and verify
Add a ~ring~-pulling dependency (any ~cc~-crate C dep) to a spawn and build
~.#packages.x86_64-linux.<crate>-aarch64-darwin~ and ~-x86_64-darwin~.  It
should compile the C deps via ~zig cc~ with no ~gcc: unrecognized … '-arch'~
errors.

** Notes
- Only affects workspaces with C-compiling deps; the template's archetype crates
  have none, which is why it surfaced only once sonify-health (TLS → ~ring~) ran
  the release-artifacts build.
- Affects both darwin targets; each has its own deps build.
- Unrelated to the concurrent ~magic-nix-cache~ ~HTTP 418~ throttling in the
  same CI run — that is a separate infrastructure issue, addressed under
  /Migrate CI off the deprecated Magic Nix Cache/ above.

* TODO Reliable launchd reload for Darwin user-agent services

nix-darwin's activation reloads launchd units with the legacy =launchctl load
-w= / =unload= API (=modules/system/launchd.nix=), which is unreliable for *user
agents* on modern macOS: the agent lives in the user's =gui/<uid>= (Aqua)
domain, but activation runs as root, and that domain only exists while the user
is logged into a GUI session.  The net effect is that a deployed plist change
gets written but the running agent is never cycled — it only picks up the change
on the next reboot/login.

Root/system daemons (the =system= domain, addressable directly from the root
activation) are largely unaffected, which is why =nix/lib/mkDarwinService.nix= —
which emits root services — does not hit this.  It surfaced in sytter, which
hand-rolls a =launchd.user.agents= agent: every deploy needed a manual
=launchctl bootout gui/$uid/<label> && launchctl bootstrap gui/$uid <plist>=.

If the template grows a user-agent Darwin service helper (or sytter-style agents
adopt =mkDarwinService=), bake in a =postActivation= reload shim that does the
modern =bootout= + =bootstrap gui/<uid>= dance, guarded on an active GUI session
for the target user.  Leave root/system services on the standard path.

Use the service's configured health endpoint as the liveness signal — the helper
already knows it (it drives the optional healthcheck agent).  After =bootout=,
poll the health URL until it stops answering (service genuinely down) before
=bootstrap=; after =bootstrap=, poll until it returns healthy to confirm the
reload actually landed, and fail the activation loudly if it does not — rather
than fire-and-forget leaving a dead agent (the exact failure mode that hid
sytter's breakage).  Caveats: =Input/output error (5)= is launchd finishing its
domain teardown, which can lag process exit slightly, so still wrap =bootstrap=
in a bounded retry; and when no health URL is configured, fall back to a
TCP-connect (or =launchctl print= state) probe.

The general fix belongs upstream (nix-darwin#1255 "Broken LaunchAgents with
launchctl 2.0"; #1199 "manually removed units not re-added"); the template shim
is the pragmatic local workaround until that lands.

* TODO Published lib crates ship a README to crates.io, generated at publish time

Published crates render "No README is published for this crate" on crates.io.
Observed on =sonify-health-server=, but it is systemic: no crate the template
emits — nor the foundation crates this repo publishes — carries a README.

** Diagnosis: not the publish workflow

=cargo publish= already bundles a README into the =.crate= tarball whenever one
exists, either via a ~readme = "..."~ field or by auto-detecting a =README.md= /
=README.txt= / =README= at the crate root; crates.io then renders it.  So
=reusable-publish.yml= needs no change to /carry/ a README.  The gap is
upstream: the crate archetypes (=template/crates/*=) ship neither a =readme=
field nor a README file at the crate root, so there is nothing for cargo to
bundle.  The only READMEs in the repo are =template/README.org= (project root)
and the cargo-husky one — neither lives at a crate root.

** Constraint: org convention vs. a Markdown renderer

crates.io renders READMEs as CommonMark, and cargo's /auto-detection/ only picks
up =README.md= / =.txt= / =README= — it will *not* auto-detect a =README.org=.
Committing a Markdown README at each crate root would break the repo's org-first
convention for that file.  This is the one spot where the convention genuinely
collides with an external renderer.

** Chosen approach: generate =README.md= at publish time, uncommitted

Author =README.org= (committed, reviewable, single source of truth) at the crate
root, and convert it to =README.md= /in the publish job/ just before =cargo
publish=.  =cargo publish= packages from the working tree, not from git, so a
file generated onto the runner's disk is bundled into the tarball and uploaded
without ever being committed — on an ephemeral CI runner it vanishes with the
runner.  The generated =.md= is a pure build artifact, like the changelog roll's
output.

Mechanics:
- Rely on cargo's auto-detection — do *not* set a ~readme =~ field.  A committed
  ~readme = "README.md"~ would make local =cargo package= / dry-runs error with
  "README file not found" when the generated file is absent; auto-detection
  silently skips when absent and picks it up when present.
- The workflow ordering already cooperates: "Commit and push release" (version
  bump + changelog) runs /before/ "Publish workspace to crates.io", so the tree
  is clean at publish time.  Generating =README.md= after that commit makes the
  tree dirty with /only/ those files — a contained blast radius for ~cargo
  publish --workspace --allow-dirty~.
- Add an org→Markdown converter to the =ci= devShell.  =mkCiShell=
  (=nix/lib/mkCiShell.nix=) currently carries only the toolchain,
  changelog-roller, and cargo-semver-checks — none can convert.  ~pandoc --from
  org --to gfm~ is the light choice; emacs org-export has higher org fidelity
  but is a much heavier dependency.  Lean pandoc.
- New publish-job step, after the release commit and before publish: for each
  publishable crate, ~pandoc --from org --to gfm --output <crate>/README.md
  <crate>/README.org~.  The job already computes the publishable set via =cargo
  metadata= for the OIDC gate — reuse it to know which crate dirs to convert.

** Scope: =lib= archetype only

Only libraries are worth publishing to crates.io; the =cli= and =server=
archetypes emit executables that nobody consumes as a dependency (and both ship
~publish = []~ by default).  So the =README.org= source and the generation step
target the =lib= archetype only — =template/crates/lib= gets a templated
=README.org= (name/description substituted at spawn time), and this repo's
publishable lib crates (=rust-template-foundation=,
=rust-template-foundation-derive=) get one so the repo dogfoods it.

** Caveats to bake into comments

- ~--allow-dirty~ widens what can ship: it disables cargo's "everything
  published is committed" guard for the /whole/ tree, not just the READMEs.  In
  a fresh CI checkout right after a scripted commit that is fine, but it is a
  real loosening — comment it at the call site so the intent is unmistakable.
- pandoc's org→gfm is good but not perfect for org-specific constructs; keep
  archetype READMEs to constructs that round-trip cleanly.

The log directory must exist before launchd starts the agent.  Use an activation

#+begin_src nix
system.activationScripts.postActivation.text = ''
  mkdir --parents /var/log/<service>
  chmod 755 /var/log/<service>
'';
#+end_src

While not included here, you will also need to ~chown~ the directory if this is
a user service.

** launchd plist

~serviceConfig~:

#+begin_src nix
StandardOutPath = "/var/log/<service>/<service>.log";
StandardErrorPath = "/var/log/<service>/<service>.log";
#+end_src

** Log rotation via newsyslog

macOS ships ~newsyslog~ which reads drop-in configs from ~/etc/newsyslog.d/~.
Add a config via ~environment.etc~:

#+begin_src nix
environment.etc."newsyslog.d/<service>.conf".text = ''
  # logfilename                          mode count size  when flags
  /var/log/<service>/<service>.log        644  5     10240 *    NJ
'';
#+end_src

- ~N~ = no signal (the service isn't syslogd; it re-opens the file on next
  write).
- ~J~ = bzip2 compression for rotated archives.
- ~size~ is in KB (10240 = 10 MB).
- ~count~ is the number of rotated archives to keep.

Adjust ~count~ and ~size~ per service — high-volume services (e.g. Ollama
inference server) need more generous limits than one-shot helpers.

* DONE ~mkDarwinCrossPackages~: build macOS release binaries on Linux

Landed in v0.19.0: the function ships in =nix/lib/mkDarwinCrossPackages.nix=,

(Linux gnu/musl + cross-compiled =aarch64-darwin= / =x86_64-darwin=), each a
signed, attested, verified-running Mach-O, with no macOS runner touched.  The
libSystem tier is dogfooded by this repo's own =compliance-cli= on every
release; the framework tier was proven on =sonify-health= (its =appleSdk= pilot
is the follow-up below).  Original design notes retained for reference:

Cross-compile the darwin release binaries on Linux runners instead of GitHub's
scarce, slow macOS runners (a free-tier =x86_64-darwin= job sat queued for
hours, never producing an artifact).  The whole approach was proven end to end
with a throwaway probe (=~/dev/darwin-cross-probe=); this entry records the
recipe so it can become a real foundation-lib function.  The probe cross-built,
on Linux builders, three running signed Mach-O =aarch64-apple-darwin= binaries:
=hello= and the repo's own =compliance-cli= (libSystem-only, on a Raspberry Pi),
and =sonify-health='s cli (=cpal= -> CoreAudio/AudioToolbox, on an x86_64-linux
box).  All three ran natively on Apple Silicon.

** Design: a third ~mk*Packages~ sibling

~mkDarwinCrossPackages~ sits beside ~mkRustPackages~ (native) and
~mkMuslPackages~ (static-musl variant), and follows the same shape: it yields
outputs only when the build platform is Linux and returns an empty set
otherwise.  The release-binaries CI matrix's darwin rows then move from macOS
runners building =.#packages.<darwin>.<crate>= natively to Linux runners
building the cross attr.  The native darwin path stays for Mac-local dev and as
a reproducibility oracle; it just leaves the artifact-production critical path.

** The proven recipe

- Build platform is =x86_64-linux= specifically — not "any Linux".  The
  =apple-sdk= deps fail to build on =aarch64-linux= (=libsbuf= meson breakage);
  =x86_64-linux= is also what GitHub CI provides.  (libSystem-only crates do
  cross fine on =aarch64-linux= — the Pi proved it — but the framework SDK does
  not, so standardise on =x86_64-linux=.)
- Codegen: rustc with the =aarch64-apple-darwin= target added via rust-overlay
  (=rust-bin...override { targets = [...]; }=), exactly as ~mkMuslPackages~ adds
  the musl target.
- Linker: =zig= via =cargo-zigbuild=.  This is the crux — nixpkgs' native cross
  stdenv is blocked because =cctools= (Apple's =ld64=) is darwin-gated
  (=meta.platforms= excludes Linux); zig ships its own Mach-O linker that runs
  on Linux and sidesteps it entirely.
- Startup/runtime glue and ad-hoc code signing come free from zig — the linked
  binaries carry =flags=0x20002(adhoc,linker-signed)=, which is what lets an
  arm64 Mach-O execute at all.  No =codesign= / =rcodesign= step needed.
- libSystem-only crates need *no* Apple SDK: zig bundles the libSystem stubs.
  This is the clean, license-free path and should be the default.
- Framework crates need Apple's interface data — headers (for any bindgen) and
  =.tbd= link stubs.  Crucially this is *inert fetched data*, available as
  =pkgs.apple-sdk.src= (a plain =fetchurl= of =MacOSX<ver>.sdk=).  The full
  =apple-sdk= package does *not* build on Linux (its =Csu= component shells out
  to =clang=, absent on a gcc stdenv), but we never need the assembled package —
  only its =.src=, which realises on Linux as a copy-not-compile step and
  carries the CoreAudio/AudioToolbox frameworks.  So consume =apple-sdk.src=
  directly; do not fight the wrapper.
- zig's Mach-O linker does not derive the framework search path from
  =-isysroot=, so the framework path must be handed to the linker explicitly,
  target-scoped so host proc-macro links keep the native linker:
  =CARGO_TARGET_AARCH64_APPLE_DARWIN_RUSTFLAGS= =
  ="-Clink-arg=-F${sdk}/System/Library/Frameworks -Clink-arg=-L${sdk}/usr/lib"=.
- Dep vendoring via crane's ~vendorCargoDeps~ so the build runs offline in the
  sandbox (the git =orgize= dep vendored cleanly this way).

** The SDK is passed as a derivation, not a boolean

~mkDarwinCrossPackages~ takes a per-call ~appleSdk~ argument that is the SDK
*derivation* (default ~null~), not a flag.  When it is set the function wires
=SDKROOT= + the framework search path; when it is null the build is pure zig
with no SDK — the clean, licence-free path for projects whose executables only
hit libSystem (the =cli= archetype, =compliance-cli=, most tools).  Passing a
derivation rather than a boolean avoids special-casing, and leaves room to one
day pass a pinned version (=apple-sdk_15.src=) or a non-nixpkgs SDK.

Rejected the boolean (and the Cargo.lock auto-detect) deliberately: the SDK is
genuinely not free, so it cannot be always-on (that would force =allowUnfree=
fleet-wide), and auto-detecting "does a crate link frameworks" is too much magic
for something this consequential — the framework need lives only in the crates'
build-time link directives, with no Nix-level marker (it is implicit in the
native darwin stdenv), so any auto-detect would be a heuristic lockfile scan.

The cross-build itself is *always on* — it is strictly better than macOS runners
and free for libSystem executables, so the template-emitted =flake.nix= always
calls ~mkDarwinCrossPackages~ (beside ~mkMuslPackages~), with no =appleSdk=.  A
project that links Apple frameworks (anything pulling =cpal=, =objc2-*=,
=core-foundation=, =security-framework=, =coreaudio-sys=, …) — and note this is
not CLI-specific; the =server= crate links them just as readily — touches two
visible spots in its own =flake.nix=:
1. its nixpkgs import gains =config.allowUnfree = true= and
   =config.allowUnsupportedSystem = true= (the latter whenever that =pkgs= is
   non-darwin, i.e. Linux CI), because =apple-sdk= is unfree and darwin-gated;
2. it passes =appleSdk = pkgs.apple-sdk.src= to the already-present
   ~mkDarwinCrossPackages~ call.  Keeping the unfree acceptance in the spawn's
   own =pkgs= config is a feature: the licence consent is visible in the spawn's
   file, not smuggled into a foundation boolean.  =apple-sdk.src= is a
   =fetchurl= (content-addressed, platform- independent output), so the
   consumer's =pkgs.apple-sdk.src= realises fine on the x86_64-linux builder
   regardless of which =pkgs= it came from.  The matrix wiring lives in
   =.github/workflows/reusable-release-binaries.yml= once implemented.

* TODO Mark internal-only commits so they do not cut a release
Every push to =main= cuts a release: a minor version bump, a crates.io publish,
and a release-binaries build.  Some commits produce *no outward-facing change* —
the build output is byte-for-byte identical to the prior release.  Adding an
internal test crate (the =darwin-cross-probe= idea), flipping a =tasks.org= TODO
to DONE, or an internal-only documentation edit all fall here.  Cutting a full
release for these — a new crates.io version nobody needs, a fresh binary build —
is waste.  We want a way to mark such a commit as internal-only so the publish
pipeline skips the version bump / publish / binary build (or skips the release
entirely).

Design notes:
- The honest test is *artifact byte-identity*, not "it's only docs".  This ties
  to the reproducibility thread from the build-provenance work: a reproducible
  build lets the pipeline /verify/ the claim (rebuild the prior release's
  artifact and diff) rather than trust a label.  A weaker first cut is a
  path-based guard — the commit touches nothing under the artifact-affecting
  paths (=crates/=, =Cargo.*=, build inputs) — but the binary-match check is the
  real guarantee.
- Not all documentation is internal-only.  =CONTRIBUTING.org=, =tasks.org=, and
  =README.org= never ship, so they qualify; but anything that lands /in/ the
  distributed artifact does not — e.g. man pages once we ship them (see the
  man-page task below), or embedded help text.  The marker must key on "does the
  artifact change", not "is this a doc".
- An internal-only commit also has no changelog entry (nothing user-facing),
  which currently trips the =changelog-required= CI gate.  The same marker
  should exempt it from that gate — the principled resolution of the tension
  where a docs-only or internal PR is forced to invent a changelog entry.
- Open questions: how the marker is expressed (a commit trailer, a PR label, a
  =rust-template.json= flag?), how =publish.yml= detects it, and whether it
  skips the whole release or only the version bump + publish while still
  attaching binaries.

* TODO Build artifacts once on the branch, promote them at release
The magic-wand build architecture: a feature branch does /everything/ a release
does — builds every artifact across every target — but stores them instead of
publishing.  A merge means "main and the branch are now the same repo state", so
main should not re-run the tests and builds that already gated the merge; the
release should just flip a bit marking the cached artifacts public.  This is the
grand version of the internal-only-commit task above; both turn on /artifact
byte-identity/.

How much Nix already gives us, and what blocks the rest:
- Nix store paths are content-addressed by their inputs, so a branch build
  pushed to a shared binary cache /is/ the "store it somewhere" mechanism, and
  main building the same tree is a cache *substitution*, not a rebuild.  "Flip a
  bit to release" becomes "the publish job uploads the already-built store
  path".  So the substrate exists; we are not starting from zero.
- The specific thing that breaks byte-identity in our pipeline is the
  version-bump release commit: the branch builds at the pre-bump version, the
  release rewrites =Cargo.toml= and rebuilds, and cargo bakes
  =CARGO_PKG_VERSION= into the binary — so the released artifact genuinely
  differs from what the branch built.  Injecting the version at publish time
  instead of committing it into =Cargo.toml= would make the branch artifact
  bit-identical to the release, but that is an invasive change to how versioning
  works.
- GitHub's other two walls: a merge creates a new commit (a fast-forward or
  squash keeps the tree content identical, so the Nix source hash matches; the
  =[skip ci]= bump commit does not), and Actions has no native "promote a
  previously-built artifact" verb.  Operator flagged this is probably not fully
  achievable without fighting Actions, so this is a direction/someday, not a
  committed plan.
- DONE — near-term stepping stone: PR CI now builds every x86_64-producible
  release artifact (the =release-artifacts= job in =ci.yml=), so a branch proves
  the artifacts build even though =main= still rebuilds them.  The rest of this

Refinement — the predictive "release-candidate" branch.  Rather than relying on
a persistent Nix cache (which needs private infrastructure, with the attendant
trust and operational cost), exploit that our versioning is /predictable/ (next
= minor + 1).  After a PR's checks pass, spin a release-candidate branch off it
that does the whole release prep speculatively: "if this merged now it would be
=v0.19.0=", so bump =Cargo.toml=/=Cargo.lock=, roll the changelog, tag, and
build the =v0.19.0= artifacts — the exact bytes main would produce.  This
dissolves the version-bump byte-identity problem above, because the artifact is
built /at/ the post-bump version, not before it.  Merge then degenerates to a
promote:
- The binaries persist with no private cache — attach them to a *draft* GitHub
  release; merging publishes the draft.  crates.io can be upload-not-rebuild
  too: =cargo package= produces the exact =.crate= on the RC branch, and the
  publish step just uploads that file.
- Main does almost nothing: fast-forward to the RC tip (the bump, changelog, and
  tag commits already exist there, so no =[skip ci]= commit is needed), publish
  the draft release, upload the prebuilt =.crate=.  No rebuild.
- The version prediction is only valid against the actual =main= tip, so two PRs
  that both predict =v0.19.0= would collide.  Two ways to serialize:
  - A formal GitHub merge queue.
  - Lighter, and preferred here: an invalidate-and-regenerate loop.  When A
    merges, delete every other open PR's now-stale RC branch (B predicted
    =v0.19.0=, which is taken).  B must rebase onto the new =main= anyway — that
    required rebase is the trigger to regenerate B's RC, now predicting
    =v0.20.0=.  So the RC generation is uniform: "after a PR's checks pass on
    any push (including a rebase), build its RC at the current predicted
    version", plus "on merge, drop the other PRs' RCs."  The only waste is the
    loser's speculative build, thrown away and rebuilt on rebase.  For this
    fleet that churn is rare: human PRs are effectively one-at-a-time, and
    dependabot PRs go through the same RC flow but do not pile up because the
    existing dependabot auto-merge drains them serially as each goes green — so
    the invalidate-and-regenerate loop just runs automatically as they clear,
    rather than accumulating into a parallel backlog.  That is why the lighter
    loop beats standing up a merge queue.

* DONE mkGnuPortablePackages cannot link a modern-glibc host shared library

The =-gnu= portable build failed to link against any nixpkgs shared library
whose glibc floor exceeds our 2.17 pin — exactly the case the helper's own doc
comment advertises (ALSA's =libasound=, PulseAudio, GL, CUDA).  A spawn's
=Release artifacts build= job failed only on the =-gnu= target with:

: ld.lld: error: undefined reference: lstat64@GLIBC_2.33
:   >>> referenced by …/libasound.so (disallowed by --no-allow-shlib-undefined)
: … dlsym@GLIBC_2.34 … pow@GLIBC_2.29 … __isoc23_strtoul@GLIBC_2.38 …

Cause: =mkGnuPortablePackages= floors the zig link at glibc 2.17, but a
=libasound.so= handed in via =buildInputs= is nixpkgs' copy, built against a
modern glibc, so it carries undefined references to post-2.17 symbols.  Those
are /not/ the portable binary's own dependencies — they are resolved at runtime
by the host's glibc and the host's =libasound.so.2=, which is the whole point of
a portable-dynamic build linking host shared objects by soname.  But zig's lld
links executables with =--no-allow-shlib-undefined= and tries to satisfy a
shared library's own undefined symbols against the 2.17 stubs, cannot, and fails
the link.

Fixed by setting a target-scoped =CARGO_TARGET_<TRIPLE>_RUSTFLAGS= to
=-Clink-arg=-Wl,--allow-shlib-undefined= in =gnuArgs=, which restores lld's
tolerance for undefined symbols that live in shared libraries (symbols undefined
in the crate's own objects still error).  =--allow-shlib-undefined= is the exact
inverse of the =--no-allow-shlib-undefined= check that failed, so it is the
surgical toggle rather than the broader
=--unresolved-symbols=ignore-in-shared-libs=.  It is target-scoped — not global
=RUSTFLAGS= — so host build-script links keep the strict default, mirroring how
=mkDarwinCrossPackages= already sets its per-target RUSTFLAGS env var.

Regression fixture: the bug escaped because no workspace crate linked such a
library.  =crates/cross-fixture= (the existing darwin-cross guard) now links
=libasound= in its =<name>-gnu= build, and =.github/workflows/ci.yml= builds
=cross-fixture-gnu= so a regression in the =--allow-shlib-undefined= handling
fails the PR on the Linux runner.

The first cut wired this as a Linux-gated =alsa-sys= dependency; CI rejected it,
and correctly.  A =cfg(target_os = "linux")= Cargo dependency is active on the
Linux CI host for /every/ workspace build — =cargo test=, =cargo clippy=, and
crane's shared deps-only build — none of which carry alsa, so =alsa-sys='s
pkg-config probe panicked and broke Test, Clippy, and the compliance-cli release
build alike.  (The darwin guard =ring= dodges this only because it is
macos-gated and thus inert on the Linux host.)  The fix keeps libasound out of
the workspace graph entirely: =cross-fixture='s =build.rs= emits the =-lasound=
link and a =link_asound= cfg only when the gnu-portable build hands it
=CROSS_FIXTURE_ASOUND_LIBDIR= (=flake.nix=, pointing at =${alsa-lib}/lib=), so
the host library is confined to the one build that supplies it.  A local extern
declaration replaces the =alsa-sys= bindings, and =build.rs= registers the cfg
with =rustc-check-cfg= so its use is not an unexpected-cfg warning under =-D
warnings=.

The single =nix/lib/mkGnuPortablePackages.nix= serves both this repo and every
spawn (via =foundation.lib=), so the one fix covers all consumers.
