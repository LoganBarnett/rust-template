* DONE Reusable CI checks should gate branch pushes, not just pull requests
The reusable workflow's ~changelog~ and ~abi~ jobs both gate on
~github.event_name == 'pull_request'~, so a contributor who pushes directly to a
long-lived branch (or to ~main~ via a non-PR flow) bypasses both the
changelog-entry requirement and the ABI / Upcoming → Breaking gate. CI should
fail the build in those cases too — the asymmetric "ABI break ⇒ Breaking entry"
rule is only useful if it holds on every path into ~main~.

Decide on the right base ref to diff against when the trigger is a ~push~
(probably ~origin/main~ for branch pushes; for pushes to ~main~ itself, either
the previous commit on ~main~ or skip with a clear reason), then drop the
~pull_request~ gate from both jobs in =.github/workflows/reusable-ci.yml=.

* DONE Automate crates.io trusted-publishing setup across the fleet
Setting up trusted publishing on crates.io is a per-crate operation: each crate
must be claimed (initial publish) and then have a publisher config registered at
=https://crates.io/crates/<name>/settings/new-trusted-publisher=.  For a single
project with one crate this is fine; for ~22 projects averaging 3-4 crates each
(60+ configs total) the UI click-through is untenable.

Both halves of the setup are scriptable via a single API token scoped to
=publish-new= and =trusted-publishing= (with crate scope left unrestricted so it
covers every crate the user owns):

- Claiming names: =cargo publish --package <crate>= using the token.
- Registering trust configs: =POST /api/v1/trustpub/github_configs= with body
  =github_config: { krate, repository_owner, repository_name, workflow_filename,
  environment? }=.

Write a helper script (e.g. =trusted-publish-setup.sh= at the repo root, or a
sub-command of an existing tool) that takes a project directory, reads its
workspace crate names from =Cargo.toml=, derives the GitHub =owner/repo= from
the project's git remote, and loops over the crates running both the publish and
the API call.  The token comes from an env var and is never persisted.

Cross-reference: depends on the existing [[*Publish crates for public projects][Publish crates for public projects]] task
for the =publish.yml= workflow the trust configs authorize.

* DONE Reusable publish workflow should create an annotated tag per release
The reusable publish workflow (=reusable-publish.yml=) does version bump →
changelog roll → release commit ("chore: release vX.Y.Z [skip ci]") → cargo
publish, but never creates a git tag.  Downstream consumers lose the
conventional way to refer to a release: =git checkout v0.3.0=, GitHub Releases
binding, =git describe=, and signing/verification tools that expect a tag
object.

Add a tagging step that creates an *annotated* tag — =git tag --annotate
v${VERSION} --message "Release v${VERSION}"= — and pushes it.  Annotated
specifically, not a lightweight tag pointing at the commit object directly: =git
describe= only walks annotated tags by default, GitHub's Releases UI
distinguishes them, and tools that inspect tag metadata read the annotation
payload.

Open design question: tag before or after =cargo publish=?  Tagging first
reserves the version even if the publish fails (which leaves a tag pointing at a
version that never made it to crates.io); tagging after means a brief window
where the crate is live but no tag exists yet.  Pick whichever failure mode is
less bad.

* DONE Reusable publish workflow should skip cargo publish when publish = false
The reusable publish workflow (=reusable-publish.yml=) always runs =cargo
publish= as its final step.  When the target crate is marked =publish = false=
in its =Cargo.toml=, cargo exits 101 with "package.publish must be set to true
or a non-empty list", and the whole workflow run turns red — once per merge to
main, indefinitely, until the consumer flips the flag.

For a downstream project that uses =publish = false= as the "not ready to
publish yet" signal but still wants the version bump → changelog roll → release
commit half of the workflow on every merge, every run is a false alarm. Add a
guard before the publish step that reads =package.publish= for the target crate
and skips =cargo publish= when the crate is not publishable.

Detection is clean via =cargo metadata --format-version 1 --no-deps=: =.publish=
is =null= for default-publishable crates, an empty array =[]= when =publish =
false=, and a list like =["crates-io"]= when restricted to specific registries.
A jq one-liner: not-publishable when =(.packages[] | select(.name == "<crate>")
| .publish) == []=.

The bump/changelog/release-commit steps stay unguarded — that is the whole
point; consumers want the release cadence even before they're ready to publish
to crates.io.

* DONE Darwin services must log to /var/log/<service>/ with rotation
Implemented in =nix/lib/mkDarwinService.nix=: log directory creation lives in
~system.activationScripts.postActivation~, ~StandardOutPath~ /
~StandardErrorPath~ on both the main service and the optional health-check agent
point at =/var/log/<service>/=, and
~environment.etc."newsyslog.d/<service>.conf"~ adds newsyslog rotation rules for
stdout, stderr, and (when enabled) the healthcheck log pair.  Notes preserved
below for future reference and for any new darwin-only services that don't go
through ~mkDarwinService~.

All darwin launchd services should write ~StandardOutPath~ and
~StandardErrorPath~ to ~/var/log/<service>/~ rather than ~/tmp/~ or nowhere.
~/tmp/~ is cleared on reboot and is not where service logs belong. Without
explicit log paths, launchd silently discards all output — making post-mortem
diagnosis impossible.

** Log directory creation

The log directory must exist before launchd starts the agent.  Use an activation
script in the module's ~config~ block:

#+begin_src nix
system.activationScripts.postActivation.text = ''
  mkdir --parents /var/log/<service>
  chmod 755 /var/log/<service>
'';
#+end_src

While not included here, you will also need to ~chown~ the directory if this is
a user service.

** launchd plist

Set both ~StandardOutPath~ and ~StandardErrorPath~ in the agent's
~serviceConfig~:

#+begin_src nix
StandardOutPath = "/var/log/<service>/<service>.log";
StandardErrorPath = "/var/log/<service>/<service>.log";
#+end_src

** Log rotation via newsyslog

macOS ships ~newsyslog~ which reads drop-in configs from ~/etc/newsyslog.d/~.
Add a config via ~environment.etc~:

#+begin_src nix
environment.etc."newsyslog.d/<service>.conf".text = ''
  # logfilename                          mode count size  when flags
  /var/log/<service>/<service>.log        644  5     10240 *    NJ
'';
#+end_src

- ~N~ = no signal (the service isn't syslogd; it re-opens the file on next
  write).
- ~J~ = bzip2 compression for rotated archives.
- ~size~ is in KB (10240 = 10 MB).
- ~count~ is the number of rotated archives to keep.

Adjust ~count~ and ~size~ per service — high-volume services (e.g. Ollama
inference server) need more generous limits than one-shot helpers.

** Reference commit

See =dotfiles= commit =a223015e= (~fix(ollama): add launchd log output with
newsyslog rotation~) for a working example applied to the Ollama darwin module.

* DONE MergeConfig derive macro
Auto-generate the ~CliRaw -> ConfigFileRaw -> Config~ merge from a single type
definition. The ~#[derive(MergeConfig)]~ macro should produce the ~CliRaw~ (clap
Parser), ~ConfigFileRaw~ (serde Deserialize), ~ConfigError~, the
~from_cli_and_file~ resolution function, and the ~CliApp~ trait impl from a
single annotated ~Config~ struct.

** API design

Struct attributes:
- ~app_name = "name"~ — required, used for ~find_config_file~ and
  ~CliApp::app_name~
- ~extra_cli = "Type"~ — optional type flattened into generated ~CliRaw~
- ~extra_file = "Type"~ — optional type flattened into generated ~ConfigFileRaw~

Field attributes:
- ~common~ — log_level / log_format; resolved via ~resolve_log_settings~ against
  ~CommonConfigFile~
- ~env~ — derived env-var name ~<app>_<flag>~ (lowercase, POSIX §8.1)
- ~env = "literal"~ — explicit env-var name (rare; for non-derivable contracts)
- ~name = "field"~ — CLI/file field name (defaults to struct field name)
- ~short = 'x'~ — short flag for clap
- ~default = "expr"~ — default value expression
- ~required~ — error if not provided (no default)
- ~parse~ — CLI/file type is ~String~, parsed via ~FromStr~ to field type
- ~skip~ — not auto-merged; calls ~Config::resolve_<field>(cli, file)~
- ~cli_only~ — not in config file

Generated items:
1. ~CliRaw~ struct (~#[derive(Debug, clap::Parser)]~)
2. ~ConfigFileRaw~ struct (~#[derive(Debug, serde::Deserialize, Default)]~)
3. ~ConfigError~ enum (~File~ + ~Validation~ variants)
4. ~impl Config { pub fn from_cli_and_file(cli: CliRaw) -> Result<Self,
   ConfigError> }~
5. ~impl CliApp for Config~

Example (simple CLI):
#+begin_src rust :exports code
#[derive(Debug, Clone, MergeConfig)]
#[merge_config(app_name = "my-cli")]
pub struct Config {
    #[merge_config(common)]
    pub log_level: LogLevel,
    #[merge_config(common)]
    pub log_format: LogFormat,
    #[merge_config(short = 'n', default = "\"World\".to_string()")]
    pub name: String,
}
#+end_src

Example (server with OIDC):
#+begin_src rust :exports code
#[derive(Debug, Clone, MergeConfig)]
#[merge_config(
    app_name = "my-server",
    extra_cli = "OidcCliFields",
    extra_file = "OidcFileFields",
)]
pub struct Config {
    #[merge_config(common)]
    pub log_level: LogLevel,
    #[merge_config(common)]
    pub log_format: LogFormat,
    #[merge_config(name = "listen", env,
                   default = "\"127.0.0.1:3000\".to_string()", parse)]
    pub listen_address: ListenerAddress,
    #[merge_config(env,
                   default = "std::path::PathBuf::from(\"frontend/public\")")]
    pub frontend_path: std::path::PathBuf,
    #[merge_config(env, required)]
    pub base_url: String,
    #[merge_config(skip)]
    pub oidc: Option<OidcConfig>,
}
#+end_src

* DONE Service helpers should use mkDefault for overridable config
=mkNixosService= and =mkDarwinService= currently assign most of the systemd /
launchd configuration as plain values (=ExecStart=, =Type=, =User=, =Group=,
=Restart=, =RestartSec=, =environment=, =wantedBy=, =after=, =requires=, the
hardening flags, etc.).  Only =WatchdogSec= is wrapped in =lib.mkDefault=.

This forces any downstream module that needs to extend the service — for example
to inject a =--config <generated.toml>= flag into =ExecStart= or add a
project-specific environment variable — to use =lib.mkForce=, which reads as
"I'm fighting the helper" when the intent is just "extend it."  Composition is
the Nix module system's native mechanism for this; the helper should make it the
path of least resistance.

Fix: wrap every value a downstream module might reasonably want to override in
=lib.mkDefault=.  Keep plain assignment only for things that genuinely cannot be
overridden (e.g. the =description= template that hardcodes =${name}=).  Apply
the same change to =mkDarwinService=.

* DONE Document the composition pattern for service helpers
The intent of =mkNixosService= / =mkDarwinService= is that downstream modules

overriding =ExecStart= (or other items, once mkDefault is in place) when the

Without a worked example, spawned projects either re-implement their own

* DONE Pre-commit hook skips renamed files
The hook collects staged files with =git diff --staged --name-only
--diff-filter=ACM=, which filters to *A*dded / *C*opied / *M*odified and
silently excludes *R*enamed.  When =git mv= is followed by edits to the renamed
file's content (the common case), git classifies the staged change as =R= rather
than =M=, so the path never lands in =STAGED_FILES=.  treefmt is then invoked
without that file, the re-stage loop skips it, and the commit captures whatever
pre-format content the rename left behind.  The working tree later shows a diff
against HEAD once anything else triggers treefmt over the affected file, which
reads as "files get modified after the commit" — the artifact that surfaced
this.

Fix: change the filter to =ACMR= so renames are included.  Verify by staging a
=git mv= + content edit and confirming the post-commit working tree matches
HEAD.
