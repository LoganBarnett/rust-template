* Working with imports

The =Imports= section collects this repo's Claude Code /imports/, which are not
org links.  Claude Code inlines each named file into the session context before
the first turn, so those documents are already read: there is no separate step
to perform, and no judgment call to make about whether a given document is
relevant enough to open.  The section is a heading of its own so that compliance
can assert the list against a named scope rather than against a position in the
file.

** Rules for editing the import list

Do not replace an import with an ~[[file:...][=name=]]~ org link.  A link is an invitation the
agent may decline; an import is not.  Links remain correct for supporting
material — the imports are reserved for documents that every change in this repo
must be measured against.

Some mechanics worth knowing before adding an entry:

- Paths resolve relative to the file doing the importing, so ~template/llms.org~
  pulls in its own imports (~template/README.org~ and
  ~template/CONTRIBUTING.org~) on its own.
- A file reached by more than one path is inlined once, so the redundancy
  between this list and the template's own list costs nothing.  It is spelled
  out here anyway: the requirement should be legible in one place rather than
  inferred through a chain.
- Position is irrelevant to the mechanism.  Claude Code honors an import
  wherever it sits, and the imported text reaches the session before this file
  is read at all, so there is no rule about the section coming first — the
  heading carries the meaning, not the placement.
- An import is a line that is exactly ~@~ followed by the path — nothing before
  it, nothing after it.  The runner matches whole lines, not org syntax, so
  anything else — however valid as org-mode — is not an import to it: an
  indented path, a path with trailing text, a path inside a sentence.  The
  converse hazard is a line that merely /begins/ with ~@~, such as a CSS at-rule
  in an example: the runner cannot tell it from an import, even inside a
  ~#+begin_src~ block, which is why the CSS examples in
  ~template/CONTRIBUTING.org~ guard their at-rules with a leading empty comment.
  To write an import path in prose without importing it, keep it inside a
  sentence or wrap it in org verbatim markers.
- Each import is a paragraph of its own: a blank line before it and a blank line
  after it.  Two imports on adjacent lines are one org paragraph — that is how
  ~org-fmt~ reads them, and how the compliance check reads them — so the blank
  line between them is not optional.
- Order is meaningful, because the order the documents arrive in is the order
  they are read.  The template's conventions come first, then what this repo
  /is/ (~README.org~), then how to land a change here (~CONTRIBUTING.org~), then
  the template's contribution conventions that spawns inherit.

* Why =template/llms.org= governs this repo too

Those are the conventions emitted into spawned projects, and the rust-template
repo itself (the foundation crate, the foundation-derive proc-macro, the
template generation scripts) holds itself to the same standards.

The whole point of rust-template is to /capture learnings as code and config/.
Exempting this repo from its own conventions would defeat that — so when in
doubt, the template's rule applies here too.

=CONTRIBUTING.org= holds the contribution conventions this repo enforces on
every pull request — changelog entries, commit messages, dependency comments,
and the compliance gates.  These are rules to follow up front, not to rediscover
from a rejected check.

* Repo-specific additions

Guidance below applies specifically to work on the rust-template repo itself —
the files under ~template/~ (which are emitted into spawned projects, not
consumed directly), the foundation crates under ~crates/~, the generation
scripts (~new-project.sh~, ~crate-add.sh~), the compliance checker
(~crates/compliance-cli~, run via ~just compliance~), and the ~config.json~
spawn registry.

** Adding crates

Use ~crate-add.sh~ (~--type cli|lib|server~) to add an archetype crate to the
workspace.  Do not hand-write a crate from scratch or run ~new-project.sh~
(which emits an entire project) just to lift a crate out of it.

** Resolving archetype/workspace mismatches

When a crate scaffolded from a template archetype does not build against this
workspace, fix it in the shared workspace configuration (the ~workspace.package~
and ~workspace.dependencies~ tables in the root ~Cargo.toml~) rather than
editing the archetype-emitted crate files.  Those files dogfood the template;
editing them to work around the host reintroduces exactly the drift the
dogfooding is meant to catch.
