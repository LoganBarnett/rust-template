#+title:     Template Compliance
#+language:  en

A derived repository is *compliant* when its structure and infrastructure match
what this template would have emitted for that project's configuration.
Compliance is not about business logic — it is about plumbing.  A repo with no
=/healthz= route in its server crate is out of compliance; a repo whose server
crate serves a different domain than the template's placeholder is simply a real
application.

* Purpose

Compliance work arises in two situations:

1. *Retroactive adoption* — an existing project predates the template (or was
   never generated from it) and needs to be reshaped so that future template
   updates can roll in cleanly.

2. *Rolling out a template update* — a new feature was added to the template and
   needs to be propagated to repositories that were generated from an older
   version.

In both cases the work is purely additive or structural: bring in missing
infrastructure, align file layout, and clean up the crate-to-role mapping.  It
is never about removing the project's own business logic.

* LLM role during compliance work

An LLM performing compliance work must follow this discipline:

- *Map, do not judge.* Decide which target crate corresponds to which template
  role (see [[*Crate mapping]]).  Do not decide whether business features should
  move, merge, or be removed — that is for the human.
- *Enumerate gaps, then act.* Identify every compliance item that is absent from
  the mapped crate before changing anything.  Summarize the gaps to the user
  before proceeding, unless the user has explicitly asked the LLM to apply
  changes autonomously.
- *Apply infrastructure, not opinions.* Bring in the missing plumbing verbatim
  from the template.  Do not redesign the feature to suit the target codebase.
- *Leave business logic alone.* Existing route handlers, domain types, error
  variants, and application-specific configuration are not compliance items and
  must not be touched unless the user asks.
- *Preserve the project's crate names.* Compliance does not require renaming
  crates to match the template's =cli= / =server= / =lib= names.  The mapping is
  conceptual.

* Crate mapping

Each target repo has crates that play the roles the template names =cli=,
=server=, and =lib=.  The names in the target repo will differ; the roles are
what matter.

| Template role | Identifying signals |
|---------------+-----------------------------------------------------|
| =lib=         | A library crate (=lib.rs= at crate root, no =main.rs=) used by the other crates.  Every compliant repo must have at least one crate in this role. |
| =cli=         | A binary crate that parses command-line arguments with Clap and exits after completing work. |
| =server=      | A binary crate that binds a listener, serves HTTP, and runs indefinitely. |

A target repo may have more crates than the template (workers, etc.).  Extra
crates are not non-compliant; they simply do not have a direct template
counterpart. Apply the general [[*Cross-role compliance items]] to them.

* Compliance items reference

The tables below enumerate known compliance items for orientation and code
review. They are *not* the compliance checklist — the process in
[[*Compliance process]] is.  A static list in this document will drift behind the
template as it evolves, and feature-by-feature auditing is too easy to miss
things.  Use the tables to recognise what kind of infrastructure belongs where;
rely on the actual template output to decide what a given project is missing.

Items marked *required* must be present in every compliant crate of that role.
Items marked *conditional* apply only when the target crate uses the related
feature.

** Cross-role compliance items

These apply to every crate regardless of role.

| Item | Required | Description |
|------+----------+-------------|
| Workspace metadata inheritance | Required | =Cargo.toml= uses =.workspace = true= for =version=, =edition=, =authors=, =license=, =repository=. |
| Semantic error types | Required | Errors are defined with =thiserror=.  Variants name the operation, not just the underlying OS error. |
| Staged configuration | Required (binaries) | Configuration flows =CliRaw= → =ConfigFileRaw= → =Config=.  =Config= is fully validated before use. |
| =config.rs= module | Required (binaries) | Configuration logic lives in its own file, not in =main.rs=. |
| =logging.rs= module | Required (binaries) | Logging initialization lives in its own file and delegates to the lib crate's logging infrastructure. |
| Integration tests | Required | At least one integration test under =crates/<name>/tests/=. |
| =rustfmt.toml= | Required (workspace) | The workspace =rustfmt.toml= is present and unmodified. |
| Pre-commit hook | Required (workspace) | =.cargo-husky/= is present and enforces =treefmt= before commits. |
| Nix dev shell | Required (workspace) | =flake.nix= is present with a working =devShells.default=. |
| Template provenance | Required (workspace) | =rust-template.json= is present at the project root and committed.  Contains a =template_sync_hashes= list of template commit hashes, one per sync event (emission or forward port), oldest first.  The last entry is the base for the next diff-based compliance run.  Projects predating this file may start with an empty list; see [[*Compliance process]] for how the process branches on sync state. |

** =lib= crate compliance items

| Item | Required | Description |
|------+----------+-------------|
| Logging infrastructure | Required | =crates/lib/src/logging.rs= (or equivalent) exports =LogLevel=, =LogFormat=, and an =init_logging= function.  Binary crates delegate to this. |
| No =main.rs= | Required | The lib crate must not contain a =main.rs=. |

** =server= crate compliance items

| Item | Required | Description |
|------+----------+-------------|
| =/healthz= endpoint | Required | =GET /healthz= returns ={"status":"healthy"}= (or equivalent JSON).  Must be part of the =base_router=, not mixed into application routes. |
| =/metrics= endpoint | Required | =GET /metrics= returns Prometheus text-format metrics via the =prometheus= crate. |
| OpenAPI / Scalar UI | Required | =/scalar= and =/api-docs/openapi.json= are served via =aide= (with =schemars= for schema generation).  The OpenAPI document is built from =aide=-annotated routes and covers at minimum the health and metrics paths. |
| =AppState= with Prometheus registry | Required | An =AppState= struct holds an =Arc<Registry>= and at minimum an =http_requests_total= counter.  State is passed through Axum's =with_state=. |
| =web_base= module | Required | Health, metrics, OpenAPI setup, and =AppState= live in a =web_base= module (lib crate or inline module), separate from application routes and from =main.rs=. |
| =TraceLayer= | Required | =tower_http::trace::TraceLayer::new_for_http()= is applied to the router. |
| Graceful shutdown | Required | The server calls =.with_graceful_shutdown(shutdown_signal())= where =shutdown_signal= awaits both SIGINT and SIGTERM. |
| =tokio-listener= binding | Required | The listener is created via =tokio_listener::Listener::bind= and served via =tokio_listener::axum07::serve=.  This enables Unix domain socket and systemd socket-activation support. |
| Systemd notifications | Required | =systemd::notify_ready()= and =systemd::spawn_watchdog()= are called after the listener binds, before the server starts serving. |
| Single combined =listen= address | Required | The bind address is a single =--listen= argument parsed into a =tokio_listener::ListenerAddress= (default =127.0.0.1:3000=), accepting =host:port= for TCP, a filesystem path for a Unix socket, or =sd-listen= for systemd socket activation — not separate host and port arguments. |

** =cli= crate compliance items

| Item | Required | Description |
|------+----------+-------------|
| Clap for argument parsing | Required | =CliRaw= derives =clap::Parser=. |
| Exits after work | Required | The binary returns from =main= (or calls =process::exit=) after completing its task.  It does not run an event loop. |

* Compliance process

Compliance work has two processes, selected by the derived repo's sync state.
Both compare against the actual template output rather than a static checklist —
any list in this document will drift behind the template as it evolves, and
going feature by feature is too easy to miss things.  The tables in
[[*Compliance items reference]] exist for orientation, not as the audit checklist.

** Run the structural checker first

Begin every compliance pass with the automated checker (see
[[*The structural checker]]).  It catches the codified, mechanical drift — required
files, foundation wiring, the GitHub Actions machinery, the documented
=llms.org= and =CONTRIBUTING.org= sections, workspace inheritance, and the
foundation pin agreement — and names each failure by its check id, so those gaps
need no manual hunting.

#+begin_src sh :exports code
just compliance --project <target-project-name>
#+end_src

Fix everything it reports, then continue to the manual walk below.  The checker
is necessary, not sufficient: a green run still leaves prose intent and the
judgment-call reconciliations that only a diff or fresh-emission comparison can
surface.

** Determine the process

1. Open =rust-template.json= in the derived repo.
2. Inspect =template_sync_hashes=:
   - Non-empty → use [[*Diff-based compliance]] against the last entry.
   - Empty, or file absent → use [[*Fresh-emission compliance]].

** Diff-based compliance

Used when a prior sync event has recorded a commit hash.  The diff between that
hash and the template's current =HEAD= bounds the work precisely.

1. *Determine the base hash.* Take the last entry in =template_sync_hashes=.

2. *Diff the template.* In the template repository: #+begin_src sh :exports code
   git diff <last-hash>..HEAD #+end_src Every changed file is a candidate for
   porting.  Ignore changes that are clearly project-name substitutions or
   business logic unrelated to the derived project's crates.

3. *Map, enumerate, report, apply.* Follow the [[*LLM role during compliance work]]
   discipline: map each touched file to a crate role, enumerate gaps, report
   them, then apply infrastructure only.  Consult [[*Crate mapping]] when the diff
   touches role-specific files.

4. *Update the record.* Append the current template =HEAD= to
   =template_sync_hashes= in =rust-template.json= and commit the file together
   with the ported changes: #+begin_src sh :exports code git -C
   <path-to-template-repo> rev-parse HEAD #+end_src

** Fresh-emission compliance

Used when =rust-template.json= is absent or =template_sync_hashes= is empty —
the derived project predates template provenance and there is no baseline to
diff from.  A feature-by-feature walk of this document cannot catch everything
the template emits; compare against a real emission instead.

1. *Emit a fresh project in a temporary directory.* #+begin_src sh :exports code
   ./new-project.sh \ --name <target-project-name> \ --output
   /tmp/<target-project-name>-fresh \ --crates <same crate set the target uses>
   #+end_src Include =--public= if the target is public.  Use the same
   =--description= if one was recorded in the spawn manifest.

2. *File-by-file comparison.* Walk the fresh emission against the derived repo.
   For each file or directory in the emission:
   - Absent from the derived repo → propose adding it.
   - Present but divergent → propose reconciling.  Favor template content except
     where the target has legitimate customisation (business logic,
     project-specific configuration fields, domain-specific dependencies).
   - Present and equivalent → skip.

3. *Map, enumerate, report, apply.* Follow the [[*LLM role during compliance work]]
   discipline.

4. *Establish provenance.* After applying, create =rust-template.json= with
   =template_sync_hashes= containing the current template =HEAD= so subsequent
   compliance work can use the diff-based process: #+begin_src sh :exports code
   git -C <path-to-template-repo> rev-parse HEAD #+end_src

** Verification

After applying compliance changes, run the full build and test suite:
#+begin_src sh :exports code
nix develop --command cargo build --workspace
nix develop --command cargo test --workspace
#+end_src
Both must succeed with no errors before declaring compliance work done.

** Future: CHANGELOG-driven hints

A forthcoming =CHANGELOG.org= in the template will record compliance-relevant
changes per release.  Once available, it will augment — not replace — the
diff-based process above, making it easier to prioritise and group related
changes during review.

* The structural checker

Alongside the manual process above, an automated checker enforces the codified,
machine-checkable subset of compliance.  It lives in =crates/compliance-cli= and
runs against every spawn registered in =config.json=:

#+begin_src sh :exports code
just compliance                      # audit the whole fleet
just compliance --project my-app     # a single spawn
just compliance --format json        # machine-readable output
#+end_src

Each check is declared in =compliance-checks.toml= with a stable symbolic id
(e.g. =llms-template-compliance-section=) that is printed on every failure, so a
result can always be traced back to the manifest.  The checks cover required
files, foundation dependency and feature wiring, the GitHub Actions machinery
(the CI, publish, branch-protection, and dependabot-automerge workflows, plus
=dependabot.yml= and =branch-protection.json=), the foundation-driven =main= and
=config= wiring (the =foundation_main= entry attribute and the =MergeConfig=
derive with its helper attribute), the module layout and workspace inheritance,
the absence of stale =rust-template= literals, the documented sections in
=llms.org= and =CONTRIBUTING.org=, and the foundation pin agreement: the
revisions pinned in =Cargo.lock= and =flake.lock= must agree with each other
(=foundation-pins-agree=) and with the template =HEAD=
(=foundation-pins-current=).  Rust facts are read from the parsed syntax tree,
and YAML / JSON / TOML facts from the parsed value tree, narrowing to a
substring match only at the leaf.

It is the first step of both processes above (see
[[*Run the structural checker first]]), but does not replace them.  The checker
enforces what can be expressed as a structural rule; the diff and emission
comparisons remain authoritative for everything a static rule cannot capture.  A
green checker run is necessary, not sufficient, for full compliance.

** Choosing a check kind

Default to /presence/ checks — =section-exists= for a heading, =mention-present=
for a load-bearing phrase, =file-present= for a required file, and a value check
(=toml-path-equals=, =yaml-path-equals=, =toml-seq-contains=, …) for a specific
setting.  They assert that what the template lays down is /there/, without
forbidding anything a spawn adds on top.  That additive freedom is the point: a
project may extend =llms.org= with its own conventions, take on a new file type
and add a formatter to =treefmt.toml=, or grow a section — and stay compliant,
because the check verifies the required content is present rather than that the
file is unchanged.  The =treefmt= checks are the model: each asserts one shipped
formatter's wiring is present, so a spawn can add its own without tripping
anything.

Prefer the narrowest precise check that captures the convention.  Reaching for
=file-matches-template= (byte-for-byte equality with the template) is almost
always a sign the precise check has not been written yet, not that an exact
match is genuinely required — and it carries a real cost: it forbids every
additive deviation, so a spawn that legitimately extends the file fails.  Treat
an existing byte-match (=rustfmt.toml= today) as a candidate to refine into
value checks on the settings that actually matter, not a pattern to copy.  If
content genuinely must match the template exactly, justify why in the change —
that case is rare, if it arises at all.

This additive freedom is distinct from the opt-out below.  Presence checks make
/deviation by addition/ free and need no declaration; =compliance-ignores= is
for the other case — deliberately /violating/ a required rule — which must be
declared with a reason so the deviation stays honest.

** Opting out of a check

A project may deliberately deviate from what the template lays down.  To keep
the checker honest about such a case, list the check ids it should ignore under
a =compliance-ignores= key in the project's =rust-template.json=:

#+begin_src json :exports code
{
  "template_sync_hashes": ["..."],
  "compliance-ignores": [
    "llms-template-compliance-section",
    { "id": "foundation-pins-current", "reason": "pinned to v0.9 intentionally" }
  ]
}
#+end_src

Each entry is either a bare check id or an object pairing the id with a reason.
An ignored check is reported as ignored — it does not count as a failure and
does not affect the exit code.

* What compliance does not cover

- Business logic, domain types, route handlers, or application-specific
  configuration fields.
- Crate names or directory layout (=crates/server= vs =crates/my-app-server=
  etc.).
- Whether to keep or remove a crate that has no template counterpart.
- The content of =README.org= or other project documentation.
- Any decision that requires understanding the project's domain.

These are for the human.
