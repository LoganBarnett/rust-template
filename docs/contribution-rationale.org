#+title:     Contribution rationale
#+language:  en

The conventions in =template/llms.org= are stated without argument.  This
document holds the argument.  It is for the humans who maintain the rules.  It
is linked from =llms.org= and never imported into an assistant's context.

* Why the rules are bare

A model imitates the register of its context more than it obeys the precepts in
it.  A rule that says "be terse" inside four hundred words of em dashes teaches
em dashes.  The rulebook is therefore written in the style it asks for.

Rationale persuades a skeptic.  The model is not a skeptic.  It needs the rule
and an example.  Every paragraph of justification competes with the rules for
attention.  The salience of each rule falls as the section grows.  The
justification lives here for humans to review.  Each section of the rulebook
stays on one screen.

The failure mode this guards against is a document that grows by one section per
observed failure.  Each section arrives with a citation and a defense.  The
result reads as an essay.  The model writes essays back.

* Imports

** An import is not a link

The import list holds only documents that every change is measured against.  An
org link is an invitation the agent may decline.  An import is not.  Supporting
material stays a link.

** How the runner reads the list

The runner matches whole lines.  It does not parse org syntax.  An import is a
line that is exactly ~@~ followed by a path.

An indented path is not an import.

Neither is a path with trailing text or a path inside a sentence.

Any line that begins with ~@~ will trigger an import.  The runner cannot tell a
CSS at-rule from an import.

Paths resolve relative to the importing file.  A redundant entry costs nothing.

Each import is a paragraph of its own.  Two imports on adjacent lines form one
org paragraph.

Order is reading order.

* Prose

** Short sentences

A sentence holds one idea.  A hung clause, a dash, a semicolon, or a
parenthetical is a second sentence nested inside the first.  Each one asks the
reader to hold the outer sentence open while the inner one runs.

Writers describe this as a lack of restraint.  The lesson is not a character
judgement.  It is that the urge to pack a sentence runs in the wrong direction.
Restraint means splitting.  Twenty words is a guide, not a count.

** ASCII punctuation

The reader has a keyboard.  An em dash cannot be typed on it without a compose
key or a digraph.  In vim, ~f~ followed by a character seeks to it.  Nobody
seeks to a character they cannot type.  A digraph exists for the em dash.  It
costs three keystrokes and a memory.  A hyphen, a period, and a comma cost
nothing.

The existing documents were dense with em dashes.  Those documents are the
model's examples.  Scrubbing them is part of the rule.

** Two spaces after a sentence

A machine needs an unambiguous sentence boundary.  One space after a period also
follows "e.g." and "Mr.".  Two spaces follow only a sentence.  Vim's sentence
text objects rely on that.  Its ~cpoptions~ ~J~ flag names the same convention.

A formatter that strips the second space wins.  Fighting it is churn on every
save.  ~elm-format~ is one.  Single-spaced prose is matched rather than
reflowed.  A reflow is a diff with no content.  Web output is exempt.  Browsers
collapse the whitespace.

** The conclusion comes first

Linda Flower named the failure in 1979.  She called it writer-based prose: text
ordered by the writer's process of discovery rather than by what a reader needs.
She described two shapes.  The narrative retells the discovery in order.  The
survey inventories what the writer knows.  Journalism calls the symptom burying
the lede.  The military's cure is bottom line up front.

A comment written in discovery order puts the mechanism first.  The conclusion
arrives in a trailing "so" or "because" clause, or inside a parenthetical.  The
reader cannot evaluate anything until that clause.  They hold every part in
their head and then read it again.

The test is to cover everything after the first sentence.  A reader who stops
there should know the point.  If what they know is which functions get called, a
mechanism has been promoted and the conclusion is still buried.

The first sentence is also the deletion condition.  A workaround's comment opens
with the fact that forces it.  When the fact stops holding, the workaround goes.
A statement of intent gives the reader neither a claim to check nor a condition
to delete on.

Bad.  The leaked key is a relative clause in the middle.  The fix is the last
three words.

#+begin_example
reqwest's error text carries the request URL, which for a v3 key
includes the key itself; the endpoint field already names the call,
so every wrapped reqwest error drops its URL.
#+end_example

Good.  The first sentence stands alone.  The mechanism follows.

#+begin_example
A wrapped reqwest error would leak the API key.  The key travels in the
request URL.  The endpoint field already names the call, so the URL is
dropped.
#+end_example

** Altitude

Documentation has levels.  A line of code is the finest.  The README is the
coarsest.  A function's doc comment sits between.  A fact belongs at the finest
level where it still applies.

A workaround is a fact about one line.  Its justification goes beside that line.
It does not go in the function summary unless the function exists only because
of the workaround.  It never goes in the README.  A high level document that
explains a low level surprise must change when the surprise goes away.  It will
not.

The review question is whether a paragraph could move down a level and still be
found by the person who needs it.  If it could, it is at the wrong altitude.

** Summaries state the outcome

A summary completes "Calling this function ..." or "Applying this commit will
...".  It states the result, never the steps.  A script that arms, aims,
authorizes, and fires is summarized as "Fires the nukes."

A surprising step gets a comment beside the step.  Suppose you have a function
that accepts your machine description.  But if your machine description includes
a temperature that is too hot, the description is rejected with
`MIGHT_BE_A_STAR`.  So instead we use a `max` function to transform the
temperature such that the description always lands.  In this case we would
document the application of `max` and explain why: Cap temperature.  Temperature
too hot.  Error code is `MIGHT_BE_A_STAR` if over cap.  The summary still says
"Sends machine description."

Listing what a thing does is the survey shape.  "This does X, Y, and Z" goes
stale the moment Y is removed or W is added.  The briefer summary never does.

** A comment adds what the code cannot

John Ousterhout's /A Philosophy of Software Design/ makes the point.  A comment
describes what is not obvious from the code, at a different level than the code.
It adds precision the code cannot express or intuition above it.  "This assigns
foo to bar" adds neither.  It is the code kept in a second place that can go
stale.

The test is regeneration.  Given the name and the summary, a fluent reader would
write roughly this code.  Where their version matches, narration is not needed.
Where it diverges, the code met something the obvious implementation does not
survive.  That divergence is the surprise.  The comment opens with the
workaround's intent (e.g. "Work around weird temperature restriction in machine
description.").  Then the comment follows up with the nature of the problem the
workaround solves.

Precision is small and easy to miss.  It covers what an absent value means, a
unit, a boundary, and whether a number was chosen or merely had to be chosen.  A
specific number reads as tuned.  A coin flip has to say it is one.  "Unset is
off.  Any value turns it on.  2 is arbitrary." is the whole comment such a
setting needs.

The bias to watch for is narration written for a reader who cannot yet read the
code.  It is the register of tutorials and answers.  Most commented code a model
has seen is in that register.

** No tombstones

"We used to do X, but now we do Y" describes code that no longer exists.  The
test is whether an author who got it right on the first pass would have needed
the sentence.  Usually not.  The sentence goes.

The exception is the surprising case.  The obvious approach fails for a reason
the reader cannot see.  Then the comment states the fact that breaks it and the
deviation follows.  That is a conclusion-first comment, not a history.  See
[[A comment adds what the code cannot]] for a strong accounting of this.

** No comment beats a confusing one

A confusing comment costs more than none.  The reader reads it, decides it is
wrong, discards it, and then reads the code.  With no comment they read the
code.  The default when unsure is silence.  A review pass deletes comments more
often than it adds them.

** Two passes

Authors draft and then rewrite.  A model can do the same.  Only a rewrite
against a checklist changes much.  A generic "now revise" pass is anchored on
the draft and moves little.  The rulebook is the checklist.

The durable form is a lint.  ASCII punctuation and semicolons in documents and
comments can be checked mechanically.  Sentence length stays a review judgement.
The compliance checker is where such a lint belongs.

** Replies

A reply is where the writer's journey is freshest.  The investigation just
happened in discovery order.  The urge is to replay it.  The conclusion comes
first.  If something could not be verified, that is the first sentence.

The path taken is not the answer.  "I checked X, then Y, then found Z" is the
narrative shape.  Z is the answer.  X and Y belong only where they qualify it.
Numbers, commands, and quoted output go in tables or code blocks.  The claim in
the prose then stays checkable at a glance.

* Version control

** Staging is the approval signal

The index records what the reviewer has read and accepted.  Whatever stays
unstaged still needs review.  An agent that stages its own work erases that
record.  A commit made on request holds the staged set and nothing more.
Intent-to-add tracks a new path for the flake and leaves its content unstaged.
The signal survives.

* Commit messages

** The summary is imperative

Git writes its own messages in the imperative.  A merge reads "Merge branch".  A
revert reads "Revert".  Git's =Documentation/SubmittingPatches= asks the same of
every patch.  It says to write "as if you are giving orders to the codebase to
change its behavior."  A summary in any other mood is the odd one out in every
log that holds a merge or a revert.

"Applying this commit will ..." yields the imperative without naming it.  Only
the bare verb completes the sentence.  "Will adds" and "will added" do not
parse.

** The summary has no period

A summary is a title.  It is not a sentence.  SubmittingPatches says the first
line "should skip the full stop."  Git's own merge and revert summaries carry
none.

Git also suggests an "area:" prefix on the summary.  This project does not use
one.

** The body says why

The body carries the motivation.  The reviewer can always see what changed for
themselves.  The diff cannot show why the change was needed or what surrounds
it.

The body might answer a few questions.  Does the fix cost performance?  Were
other approaches considered and discarded?  Is this the first commit in a series
of similar refactors?

A fact whose value outlives the commit belongs in the code.  A workaround or a
surprising change gets a comment beside the line it guards.  The commit can call
it out as well.  See [[Altitude]].

* Code

** The biases are vague on purpose

The list of LLM code biases names no thresholds.  Each item is a judgement call
in the "I know it when I see it" sense.  A stated threshold invites code that
sits just under it.

DRY shows the problem.  A rule of "after three repetitions" lets two functions
share two hundred lines.  Repetition is also sometimes the honest form.  That
happens when the language cannot express the abstraction.  Pulling data out of a
structure in a language without lenses is one example.

** Long arguments document themselves

A long argument reads as a word.  A short one reads as a letter.  ~mkdir
--parents~ says what it does.  ~mkdir -p~ says it only to a reader who already
knows.  The long form costs the author a few characters once.  The short form
costs every reader a lookup.  Where only the short form exists, a comment at
each use pays that cost instead.

** An import names its file

A directory import makes the reader run the resolver by hand.  Nix turns ~./foo~
into ~./foo/default.nix~.  Node's ~require~ tries ~foo.js~, ~foo.json~, and
~foo.node~.  It then tries ~foo/index~ with each extension.  Bundlers add ~.mjs~
and ~.cjs~.  TypeScript adds ~.ts~, ~.tsx~, and ~.d.ts~.  For years it forbade
writing the extension at all.  Editor jump-to-definition lands on the directory
or guesses.  Node is where the scar is deepest.  Nix has one rule.  The explicit
path is still the cheap side.  Typing ~/default.nix~ costs seconds once.  The
ambiguity costs hours in a debugger.

A project that already imports directories implicitly keeps its pattern.
nixpkgs, home-manager, and nix-darwin all do.  Two styles in one tree cost more
than either alone.

* Rust

** Errors say what was happening

A semantic error names the operation that failed.  A bare file error might carry
the path.  It still does not say what the program was doing.  It signals only
that some file somewhere could not be read.  That tells contributors and users
nothing.

Bad.  Any file read in the program produces this message.

#+begin_example
Could not read file: No such file or directory (os error 2)
#+end_example

Good.  The message names the failure and the operation it interrupted.

#+begin_example
Could not read configuration file: No such file or directory (os error 2)
#+end_example

Semantic variants see little reuse.  Each one names a single operation.  That is
acceptable.

** Result is control flow, not recovery

The unwrap ban is not about recovering from errors.  A ~Result~ forces the
caller to acknowledge a failure.  The error then propagates or converts along
one visible path.  Recovery is one use of that.  Propagation and forced
acknowledgment are the rest.  An unwrap trades all of it for brevity.

Models carry an exception-friendly habit from Python and similar languages.
There an ad hoc ~try~ is normal.  Rust rejects that habit.  Shipping code either
proves unreachability to the compiler or propagates the error.  There is no
third option.

** Literals are proven at compile time

A literal regex looks safe to unwrap.  Only a typo can break it.  The first run
should catch the typo.  That assumes every path holding the unwrap runs.
Coverage is never complete.  An unwrap on a cold path ships.  The panic waits
for the rare input that reaches it.  A macro moves the check to compile time.
Any unwrap left lives in generated code on a path the macro proved unreachable.

** Every carve-out was considered

Each trap in =llms.org= once looked like a fair exception.  Each was rejected.
The arguments live here so nobody re-derives them.  "But this case is different"
is itself the warning sign.

*** Lock poisoning

A poisoned lock means another thread panicked mid-update.  Panicking again looks
idiomatic.  That is an application author's judgment.  The rule also governs
libraries.  A library that panics on poisoning takes the decision from its
caller.  That caller may be a daemon, a supervisor, or an FFI host.  Return the
error and let the caller decide.  ~parking_lot::Mutex~ has no poisoning at all.

*** Build scripts, examples, and benches

A build script runs once.  A panic fails the build loudly.  A ~Result~ there
looks like ceremony.  The ceremony is the value.  Cargo still sees a non-zero
exit and prints the error.  A build script that panics drifts toward needing
tests for its own error paths.

Examples gain nothing from an unwrap over ~?~.  Both fail loudly.  Examples are
also teaching material.  Users copy whatever they show.  Benches follow the same
logic.

*** Thread joins

A join error carries the child thread's panic.  Unwrapping it re-raises that
panic.  The unwrap looks like honest propagation.  Yet not panicking is not
swallowing.  Converting the error and returning it is the opposite of
swallowing.  The caller may want to log, retry, or report it.  When a re-raise
is the intent, ~resume_unwind~ says so.  A bare unwrap hides it.

*** The system clock

~SystemTime::now().duration_since(UNIX_EPOCH)~ fails only when the clock reads
before 1970.  That happens.  Embedded devices, freshly imaged VMs with bad
clocks, and containers without time sync all hit it.

*** Check then unwrap

An unwrap right after an emptiness check cannot fail today.  The pair rots the
first time someone refactors between the two lines.  ~if let~ moves the
invariant into the type system.

*** Always-set environment variables

A variable set in every deployment is still missing somewhere.  Local
development, a one-off script, a new environment, and a debugging shell all lack
it.  Loading config at startup can name the missing variable.

*** Initialization order

Unwrapping a ~OnceCell~ after an earlier initialization usually means the data
structure is wrong.  ~LazyLock~ exposes the value through ~Deref~.  ~OnceLock~
has ~get_or_init~.  Neither needs a runtime claim about order.

** Tests may panic

Tests are the one exemption from the unwrap ban.  A panic is the failure signal
a test wants.  A test is also not a shipping code path.

** Clippy enforces the combinator rule

Clippy enforces the mechanical half of the rule of least power.  The ~manual_*~
lints flag hand-written versions of standard combinators.  ~manual_map~,
~manual_filter~, ~manual_find~, and ~manual_let_else~ are examples.
~option_if_let_else~, ~map_unwrap_or~, ~question_mark~, and ~single_match_else~
join them.

The lints sit at ~warn~ under ~[workspace.lints.clippy]~ in the root
=Cargo.toml=.  Locally a warning does not block iteration.  CI and the
pre-review gate both run clippy with ~--deny warnings~.  There a combinator lint
blocks the merge like any other error.

Some imperative forms are genuinely clearer.  Multi-line bodies, side effects,
and nested control flow are the usual cases.  Such a site carries
~#[allow(clippy::lint_name)]~ with a one-line reason beside it.

** Maximum expressivity is the wrong default

The most expressive construct is the wrong default.  Models reach for ~match~,
~for~, and early ~return~ anyway.  Most Rust in their training reads that way.
Those constructs are also the most expressive available.  The narrowest
construct that fits comes first.  A ~match~ or a loop is the escalation.  It is
warranted only when the combinator form distorts the meaning.

** Functional style quarantines the imperative

Functional style confines imperative code to where it is unavoidable.  Rust is
imperative at its core.  Its imperative surfaces are external APIs, the disk,
the network, and output.  Nearly all the data manipulation those surfaces need
can still happen in a functional section.  The imperative part is then laid
bare.  It is not intermingled with data manipulation.  Reasoning about it
becomes easy.

Early returns hint at a data structure that needs sharpening.  A type introduced
at an earlier stage can remove the branches.  So can moving each branch into its
own function.  A function is best read as what it returns.  It is not a series
of alterations.  An early return says "no further alterations."  A branch says
"these are the ways a result is produced."

Building a list by pushing onto it is imperative.  It is a sure sign that a
combinator such as ~filter~ is missing.  Chaining several combinators is fine.
Rust optimizes iterator chains well.

A long-lived variable marks a function that is too long and does too much.
Variables marked ~mut~ are the usual case.  Not every ~mut~ is a culprit.  Many
are.  A long-lived variable also carries its own load.  The reader must assume
it can be used anywhere from its declaration to the end of its scope.

Functions are named as nouns because verbs are highly subjective in software.
The noun names what the function returns.  ~foo~ says what comes back.
~get_foo~ adds a verb that each reader interprets differently.

** Local variables are discouraged rather than banned

Rust sometimes needs a local variable.  Scope and ownership can force a binding.
A value with more than one use earns a name.

Two tools keep a chain intact without a local.  ~tap~ logs in the middle of a
call chain without breaking it.  A struct can also be built atomically from
function calls.  Its ~foo~ field takes the result of ~foo()~ directly.

** Debugging

Permanent log lines are one of the best cures for missing information.  A log
line at an appropriate level stays after the fix.  A temporary print helps only
the session that added it.

Integration tests against mock services exercise real behavior.  Unit tests tend
to exercise contrived situations.

** Candidate types

Candidate types suit processing that runs in phases.  Each phase hands the next
a type that says how much is already validated.

* Persistent memory

** Auto-memory ships off

Spawned projects ship with the assistant's auto-memory off.  The emitted
=.claude/settings.json= sets ~autoMemoryEnabled~ to ~false~.  Auto-memory
accrues files under a contributor's home directory.  Those files are
machine-local, invisible to review, and scoped to one clone.  With it off, every
learning goes through the checked-in docs.  A contributor can re-enable it per
clone for genuinely local scratch context.

* Verification

** Clippy runs before review

The clippy gate in =llms.org= is the same gate CI enforces.  Running it first
keeps a lint failure from reaching the reviewer or the pipeline.  It also
surfaces the combinator lints while the change is still in hand.
