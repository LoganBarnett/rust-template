* Working with imports

** Automatic Imports

This is for the following coding agent runners:

1. Claude Code

The documents under [[Imports]] are already in context.  Do not open them.  Do not
weigh whether any of them is relevant enough to open.  Claude Code inlines each
named file before the first turn.  An import is not an org link.  Compliance
finds the list by the [[Imports]] heading rather than by its position in the file.

** Manual Imports

If you are not listed in the coding agent runners for [[Automatic Imports]], this
applies to you.

You must read the documents listed in [[Imports]].  Report to your operator how you
handle automated imports, even if you do it the same way Claude does, so this
can be codified.

~CONTRIBUTING.org~ covers how to land a change: changelog entries, commit
messages, dependency comments, and the other conventions every pull request must
follow.  Those conventions are enforced, so rediscovering them from a failed
compliance check wastes a round trip.  ~README.org~ covers what this project is
for; a change that contradicts it is wrong even when it compiles.

** Rules for editing the import list

Claude:
1. Start with ~@~ at beginning of line.
2. Give each import a blank line before and after.
3. Keep ~@README.org~ before ~@CONTRIBUTING.org~.

The example below shows how this is done.  The comma in the raw org-mode text is
an escape character to prevent an import.

#+begin_src org :results none :exports code
,@foo-doc.org
#+end_src

* General code guidelines

These are instructions for LLMs to write code and documentation to my standard.

** Documents

When authoring new content, make them ~org-mode~ files.

Use ~:exports code~ if you just want to show off the code, and don't want it to
actually run anything.

No file lists in documentation.

** Prose rules

These apply to comments, doc comments, org documents, commit bodies, and
replies.  The rules are stated, not argued.  The reasoning behind each one is in
rust-template's [[https://github.com/LoganBarnett/rust-template/blob/main/docs/contribution-rationale.org][=docs/contribution-rationale.org=]].  That document is not
imported.

- Sentences are short.  One idea each.  About twenty words.
- Punctuation is ASCII.  No em dashes.  No semicolons.  No parentheses.
- A comma sets off one leading clause or separates a list.  Anything else is two
  sentences.
- Comments are complete sentences wrapped at 80 columns.
- Two spaces follow sentence-ending punctuation.  A formatter that strips them
  wins.  Match single-spaced prose rather than reflowing it.
- Open with the conclusion.  The mechanism comes after, or not at all.
- A fact lives at the lowest level where it applies.  A line of code is the
  lowest and the README is the highest.  A workaround is explained on the line
  it guards, never above it.
- A summary states the outcome.  It never lists the steps.
- A comment states what the code cannot.  If the code could regenerate the
  comment, delete the comment.
- Do not describe code that no longer exists.  If the obvious approach fails,
  state the fact that breaks it.
- A number that was a coin flip says so.
- When unsure whether to write a comment, do not.
- Draft prose longer than a paragraph in a scratch file.  Rewrite it against
  this list.  Only the rewrite lands.

Bad.  The problem is a relative clause in the middle and the fix is the last
three words.

#+begin_example
reqwest's error text carries the request URL, which for a v3 key
includes the key itself; the endpoint field already names the call, so
every wrapped reqwest error drops its URL.
#+end_example

Good.  The first sentence stands alone and the mechanism follows.

#+begin_example
A wrapped reqwest error would leak the API key.  The key travels in the
request URL.  The endpoint field already names the call, so the URL is
dropped.
#+end_example

** Version Control
*** Adding Files for Nix Flakes

Nix Flakes only see tracked files.  An untracked file appears as missing.  Use
~git add --intent-to-add~ to add files to allow [[Leave Unstaged]] to be honored
while satisfying Nix Flakes.

*** Commit Messages

The audience of a commit message is a reviewer.

The commit has three components: The title, the activity, and the description.

1. The title follows the ~git~ imperative style.
2. The activity is a single sentence saying what it accomplishes.  It names the
   ticket if one exists.
3. The description explains "why" and any notable, surprising bits.

In all cases, follow [[Prose rules]].

#+begin_example
frobnicate self sealing stem bolts

Closes #1234 - Self sealing stem bolts arrive unfrobnicated.

Self sealing stem bolts require frobnication.  This adds it when they are
inserted via the UI or API.
#+end_example

Do not include taxonomy of the ticket or the change.  No =feat=, no =fix=, and
the like.

*** Leave Unstaged

Files should be left unstaged for review.  See [[Adding Files for Nix Flakes]] for
an exception and how to handle it.

** Code

*** Initialisms

Use Pascal Initialisms (~Url~) instead of Preserved Initialisms (~URL~) when
_authoring_ new identifiers in camel case.

*** LLM code biases to avoid

These are reminders, not boundaries.  A model already knows each of these.  It
just needs the nudge, and the review agent needs a list to check against.

- Copying a block instead of finding, or extracting, the helper that already
  does it.
- Speculative generality: parameters, options, hooks, and abstractions nobody
  asked for, kept "for later".
- Compatibility shims nobody asked for: an old name kept as an alias, a
  deprecation path in a repo with one user.  Delete instead.
- Long functions with nested branches where extraction would name the pieces.
- Masking errors: broad handlers, ~.ok()~ or ~let _ =~ on a ~Result~, defaults
  that turn a failure into a wrong answer (see "Error Handling").
- Silencing a check instead of fixing what it found: a suppressed warning with
  no reason beside it, a weakened or deleted test.
- Calling functions, arguments, or fields that do not exist.  The compiler and
  clippy are the check; run them before offering code (see "Verification").
- Restyling or reformatting code the task did not touch.
- A test that has never been seen failing.  Run it against the code before the
  fix and show the failure, then the pass.
- Placeholders and "implement later" in shipped code.

*** Program arguments

Use a program's long arguments whenever it has them.  ~mkdir --parents~, not
~mkdir -p~.  A short argument with no long form gets a comment at each use.

*** Import paths

An import names a file, never a directory.  In Nix that is ~./foo/default.nix~,
not ~./foo~.  A project that already imports directories implicitly keeps its
pattern.

** Rust

*** Error Handling

Use semantic errors.  Do not just wrap or propagate a ~FileMissingError~ or
~FileWriteError~.  Include something about the error itself or about the process
in which it occurred.  ~ConfigFileMissingError~ names the error and
~ReportFileWriteError~ names the process.  Use ~thiserror~ to map other API
errors when sensible.  Do not employ ~anyhow~.

Do not drop or swallow errors.

*** No ~unwrap~ or ~expect~ in non-test code

Shipping code never calls ~.unwrap()~ or ~.expect()~.  The non-panicking
variants such as ~unwrap_or~ are fine.  Propagate with ~?~, convert with
~.map_err~, or handle the error.

Tests may panic.  That covers ~#[cfg(test)]~, ~#[test]~, and ~tests/~.
Examples, benches, and ~build.rs~ are not tests.  Their ~main~ returns
~Result<(), Box<dyn Error>>~.

A failure that seems impossible is proven to the compiler:

- A literal regex uses ~lazy_regex::regex!~.
- A literal address uses a ~const~ constructor such as ~Ipv4Addr::new~.
- A literal URL uses ~url-macro~.
- Any other literal gets a validating macro.  Write one if none exists.

Common traps and their fixes:

- Lock poisoning: return the error or use ~parking_lot::Mutex~.
- A thread join: convert the error or call ~std::panic::resume_unwind~.
- ~SystemTime~ before the epoch: ~.unwrap_or(Duration::ZERO)~.
- Check then unwrap: use ~if let~ or ~let else~.
- An environment variable: load config at startup and name the missing one.
- ~OnceCell~ after init: use ~LazyLock~ or ~get_or_init~.

A case that looks new is usually one of these traps in disguise.

*** Rule of least power

Choose the least expressive construct that does the job.  The principle comes
from Tim Berners-Lee: a more powerful construct can do more, and that capacity
is a /liability/ for the reader, who has to verify what it actually does versus
what a narrower construct would have constrained it to. ~Option::map~ can only
transform-if-present; ~match~ on ~Option~ can do anything, so the reader has to
read both arms to be sure.  An iterator chain constrains the work to per-element
transformation and aggregation; a ~for~ loop with mutation can do anything at
all. The narrower form carries an invariant the broader one does not.

The Rust corollary is to prefer combinators and expressions over ~match~, ~if
let~, and ~for~ when the combinator form expresses the same control flow.
Concretely:

- ~Option::map~, ~Option::and_then~, ~Option::or_else~ over ~match~ on ~Option~.
- ~Result::map~, ~Result::map_err~, and ~?~ over ~match~ on ~Result~ for
  propagation.
- Iterator chains (~map~, ~filter~, ~filter_map~, ~find~, ~fold~, ~collect~)
  over ~for~ loops with mutation.
- ~let~ over ~let mut~; pure expression over statement-with-side-effects.
- ~Option::map_or~ / ~map_or_else~ over ~if let Some(x) = ... { ... } else { ...
  }~ when both arms are pure transforms.

*** Functional Style

Code should be written in functional style whenever possible.

Avoid these imperative smells:
+ Early returns :: Instead of returning early, use the appropriate ~if/else~ or
  equivalent to show the branching pattern.
+ List building :: Instead of building up a list, reach for a compositor
  instead.
+ Long lived variables :: Avoid long living variables.  Those marked ~mut~ are
  the worst offenders.
+ Functions as verbs :: Name functions as nouns.  The noun is what is returned.
  ~sum~ returns the sum and ~reversed~ returns the reversed string.

*** Code Structure

**** Files and modules

~main.rs~ should only ever be an orchestrator.  Create sibling files for
associated functionality and have ~main.rs~ delegate to them.

Delegate obvious concerns: ~config.rs~ for configuration, ~logging.rs~ for
logging initialization.  It is okay if these wind up being a single struct and a
single function.

Keep ~.rs~ files under ~src~ for executables and ~lib~ for libraries.

**** Chains, local variables, and tap

Use ~tap~ to reduce local variable usage as well as perform logging.  Local
variables aren't disallowed but discouraged.

Use chained calls when possible.

*** Debugging

When the program lacks sufficient output to determine what is going on, improve
the logging.  The program tells you what ails it.

Create tests which exercise the problem you are running into.

Prefer mock services with full-stack integration tests over unit tests.  The
closer to real, the better.

Tests and test scripts must exit with a proper error code.  Never author
anything that makes you parse output to determine if there was an error.

*** Types as validation

Only use ~Option~ if the field is truly optional.  If a struct would be invalid
without a field set, do not use ~Option~.  Instead, make an intermediate type
that represents a candidate whose validity is not yet fully known.

For example, ~CliArgs~ can represent arguments as provided on the command line.
~ConfigFile~ can represent the configuration file's state.  Meshing the two
together yields a ~Config~ that represents a completely valid configuration.



* Persistent memory

Use the assistant's local memory only for facts specific to one clone or one
machine.  That covers local paths, machine quirks, and transient personal
context.

A project convention or decision belongs in the repository, in ~llms.org~,
~CONTRIBUTING.org~, or ~docs/~.  There every contributor benefits from it and it
can be reviewed.  Reaching for memory to record a convention is the signal that
it should be codified here instead.

* Verification

** Use the Nix development shell when available

If ~nix~ is available (~which nix~ succeeds), run all commands inside the Nix
development shell rather than using whatever toolchain is on the system PATH:

#+begin_src sh :results none :exports code
nix develop --command just build
nix develop --command just test
#+end_src

This ensures the correct Rust toolchain and associated tools (such as ~rustfmt~)
are in use.  The pre-commit hook requires ~rustfmt~ in PATH, so ~git commit~
must also go through the shell:

#+begin_src sh :results none :exports code
nix develop --command git commit --message "your message"
#+end_src

** Run all tests after changes

Run ~just test~ after making any change to verify nothing is broken.

** Run clippy before offering Rust changes for review

Any change that touches ~.rs~ files must pass the workspace clippy gate before
it is presented for review:

#+begin_src sh :results none :exports code
nix develop --command cargo clippy --workspace --all-targets --all-features \
  -- --deny warnings
#+end_src

This applies to every contributor, human or agent.  Nothing runs it on your
behalf.
