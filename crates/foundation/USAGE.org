#+title:     rust-template-foundation Usage Guide
#+language:  en

* Overview

=rust-template-foundation= provides the generic plumbing that every spawned
project needs: configuration discovery, logging, health checks, metrics,
OpenAPI, OIDC authentication, systemd integration, and a managed entry point.

The crate is organised behind feature flags so projects only pay for what they
use:

- *cli* — ~CommonConfigFile~ (file side of the CLI/file merge), CLI
  logging, the ~CliApp~ trait, the ~MergeConfig~ derive (which generates
  ~CliRaw~ inline with per-app-prefixed env vars), and the
  ~#[foundation_main]~ proc macro.
- *server* — Health registry, metrics endpoint, OpenAPI/Scalar helpers, SPA
  fallback, systemd notify/watchdog, server logging.
- *auth* (implies ~server~ + ~cli~) — OIDC login/callback/logout handlers,
  ~require_auth~ middleware, ~Server~ runner, ~ServerApp~ trait,
  ~BaseServerState~, and JWT bearer-token validation for service /
  automation callers (see [[*JWT bearer auth (automation callers)]]).

* Quick start: server

#+begin_src rustic :results none :exports code
// main.rs — the entire file
use rust_template_foundation::main as foundation_main;
use rust_template_foundation::{Server, ServerError};
use crate::config::Config;
use crate::web_base::AppState;
use std::process::ExitCode;

#[foundation_main]
pub async fn main(
    config: Config,
    server: Server,
) -> Result<ExitCode, ServerError> {
    let server = server.with_state(|base| AppState { base });
    server.listen().await?;
    Ok(ExitCode::SUCCESS)
}
#+end_src

By the time the function body runs: CLI is parsed, config is resolved, logging
is live, OIDC discovery (if configured) is complete, and the ~Server~ is ready
to have routes added.

* ~#[foundation_main]~

The proc macro examines the annotated function's signature to determine what
kind of app this is:

| Signal         | Interpretation  |
|----------------+-----------------|
| ~Server~ param | Server app      |
| No ~Server~    | CLI app         |
| ~async fn~     | Wrap in tokio   |
| ~fn~           | Direct call     |

** Generated code for server apps

1. Parse CLI via ~<Config as CliApp>::CliArgs::parse()~
2. Resolve config via ~<Config as CliApp>::from_cli(cli)~
3. Init server logging from config's log settings
4. Build tokio runtime
5. Inside ~block_on~:
   a. ~BaseServerState::init~ from first server config
   b. ~Server::new(base, config)~ for each ~ServerRunConfig~
   c. Call user's function with ~(config, server)~ or ~(config, (s1, s2))~
6. Map ~Result<ExitCode, E>~ to ~ExitCode~ (log error on ~Err~)

** Generated code for CLI apps

1. Parse CLI
2. Resolve config
3. Init CLI logging
4. Call user's function
5. Map result to ~ExitCode~

* Traits: ~CliApp~ and ~ServerApp~

** ~CliApp~

#+begin_src rustic :results none :exports code
pub trait CliApp: Sized {
    type CliArgs: clap::Parser;
    type Error: std::fmt::Display;
    fn app_name() -> &'static str;
    fn from_cli(cli: Self::CliArgs) -> Result<Self, Self::Error>;
    fn log_level(&self) -> LogLevel;
    fn log_format(&self) -> LogFormat;
}
#+end_src

Implement this on your ~Config~ type.  All apps (CLI and server) must implement
~CliApp~.

** ~ServerApp~

#+begin_src rustic :results none :exports code
pub trait ServerApp: CliApp {
    fn server_run_configs(&self) -> Vec<ServerRunConfig>;
}
#+end_src

Server apps additionally implement ~ServerApp~.  Return a ~Vec~ of one for a
single server, or ~Vec~ of N for multiple servers.

* ~Server<S>~ API

The ~Server~ type is a builder that accumulates routes and configuration before
either binding a listener (~listen()~) or producing a test router
(~into_test_router()~).

** ~Server::new(base, config)~

Create a server from shared base state and a run config.

** ~.with_state(|base| AppState { base })~

Transform to use custom application state.  The closure receives the
~BaseServerState~ and returns your custom state type.  The new state type must
implement ~FromRef~ for ~HealthRegistry~, ~Arc<Registry>~, and
~Option<Arc<CoreClient>>~ — use the ~impl_server_state!~ macro.

** ~.api_route(path, method_router)~

Add an OpenAPI-documented route using aide's ~get_with~, ~post_with~, etc.

** ~.merge(api_router)~

Merge an ~ApiRouter~ of user routes.

** ~.listen()~

Start listening.  Blocks until graceful shutdown completes.  Internally:
1. Assembles infrastructure routes (~/healthz~, ~/metrics~)
2. Merges user routes
3. Finalises OpenAPI spec
4. Builds auth routes (~/auth/login~, ~/auth/callback~, ~/auth/logout~)
5. Builds ~/me~ route
6. Applies session layer and trace layer
7. Optionally serves SPA frontend
8. Binds listener via ~tokio-listener~ (supports TCP, Unix, systemd)
9. Calls ~systemd::notify_ready()~ and ~systemd::spawn_watchdog()~
10. Serves with graceful shutdown (~SIGTERM~ / ~Ctrl+C~)

** ~.into_test_router()~

Build the complete ~Router~ without binding a listener.  Uses
~secure_cookies=false~ so plain HTTP works in tests.  Drive it with
~tower::ServiceExt::oneshot~.

** ~.base_state()~

Access the shared ~BaseServerState~.  Clone this to create additional servers
on different ports/sockets.

* ~BaseServerState~

* ~impl_server_state!~

use rust_template_foundation::{impl_server_state, server::runner::BaseServerState};

#[derive(Clone)]
pub struct AppState {

impl_server_state!(AppState, base);

Generates ~FromRef<AppState>~ for ~HealthRegistry~, ~Arc<Registry>~, and
~Option<Arc<CoreClient>>~, delegating to the named field.

* Auth behaviour

OIDC is fully optional.  When ~oidc~ is ~None~ in the ~ServerRunConfig~:

- ~/auth/login~, ~/auth/callback~, ~/auth/logout~ return 404.
- ~/me~ returns ~{"name": "admin", "auth_enabled": false}~.
- ~require_auth~ middleware passes all requests through.

To protect specific routes, apply ~require_auth~ as middleware on your route
groups:

#+begin_src rustic :results none :exports code
use rust_template_foundation::auth::require_auth;
use axum::middleware;

let protected = ApiRouter::new()
    .api_route("/api/things", get_with(list_things, ...))
    .layer(middleware::from_fn_with_state(state.clone(), require_auth));
#+end_src

* JWT bearer auth (automation callers)

Browser users authenticate via the OIDC session flow above.  Service
clients, scripts, and other automation authenticate by sending a
signed JWT in ~Authorization: Bearer <token>~, validated against an
issuer's JWKS.  This path is independent of ~require_auth~ — there is
no session cookie involved — and is intended to make automation a
first-class caller rather than an afterthought.

The building blocks live in ~rust_template_foundation::auth::jwt~ and
are intentionally not auto-wired into ~BaseServerState~: the claims
type is application-specific, so apps embed a ~Decoder<T>~ in their
own state.

** Default claims (~ServiceClaims~)

For the common case — registered claims plus a flattened map of
extras — use the bundled ~ServiceClaims~ struct:

#+begin_src rustic :results none :exports code
use axum::{Router, routing::get, extract::FromRef, Json};
use rust_template_foundation::auth::jwt::{
  build_decoder, Claims, Decoder, JwtConfig, ServiceClaims,
};

#[derive(Clone, FromRef)]
struct AppState {
  decoder: Decoder<ServiceClaims>,
}

async fn protected(claims: Claims<ServiceClaims>) -> Json<String> {
  Json(claims.claims.sub)
}

let config = JwtConfig {
  jwks_url: "https://issuer.example/.well-known/jwks.json".into(),
  issuer: "https://issuer.example/".into(),
  audiences: vec!["my-api".into()],
  algorithms: vec![jsonwebtoken::Algorithm::RS256],
};
let state = AppState { decoder: build_decoder::<ServiceClaims>(&config).await? };
let app = Router::new()
  .route("/protected", get(protected))
  .with_state(state);
#+end_src

~build_decoder~ performs the initial JWKS fetch synchronously — a
misconfigured issuer surfaces as a startup error rather than a flood
of 401s — and spawns a background refresh task whose lifetime is tied
to the process.

** Bringing your own claims struct

When you need typed access to provider-specific claims (~scope~,
~roles~, tenant identifiers, etc.), define your own struct and
parameterise ~build_decoder~ over it:

#+begin_src rustic :results none :exports code
#[derive(Clone, serde::Deserialize)]
struct MyClaims {
  sub: String,
  exp: i64,
  #[serde(default)]
  scope: String,
  tenant_id: String,
}

let decoder: Decoder<MyClaims> = build_decoder::<MyClaims>(&config).await?;
// Pair with Claims<MyClaims> in handlers.
#+end_src

The only requirement is ~T: DeserializeOwned + Send + Sync + 'static~.
The same ~RemoteJwksDecoder~ instance underneath supports any claims
type — only the trait-object coercion picks ~T~.

** Validation rules

~JwtConfig::validation()~ produces a ~jsonwebtoken::Validation~ with:

- ~algorithms~ set from the config (defaults to ~RS256~ if empty —
  empty would otherwise disable algorithm checking, which is almost
  never what you want).
- ~iss~ set to the configured issuer.
- ~aud~ set to the configured audiences (skipped if empty).
- Default ~jsonwebtoken~ behaviour for everything else — notably a
  60-second leeway on ~exp~ / ~nbf~.

The full ~Validation~ surface is exposed if you need to tweak it
(~required_spec_claims~, ~leeway~, etc.) — construct one yourself and
pass it to ~RemoteJwksDecoder::builder()~ directly instead of going
through ~build_decoder~.

* Config pattern

The recommended configuration pattern uses three stages:

1. *~CliRaw~* — parsed CLI arguments (~clap::Parser~)
2. *~ConfigFileRaw~* — deserialised config file (~serde::Deserialize~)
3. *~Config~* — validated, merged configuration

The ~Config::from_cli_and_file~ method merges CLI → config file → defaults.
Wire it into the ~CliApp~ trait via ~from_cli~.

** Subcommands

Mark a field with ~#[merge_config(subcommand)]~ to expose a clap subcommand on
the generated ~CliRaw~.  The field's type is forwarded verbatim, so required
vs. optional follows the type:

- ~pub command: Commands~ — clap requires a subcommand.
- ~pub command: Option<Commands>~ — running the binary with no subcommand
  yields ~None~.

#+begin_src rustic :results none :exports code
#[derive(clap::Args)]
pub struct PrintArgs {
    #[arg(long)]
    pub message: String,
}

#[derive(clap::Subcommand)]
pub enum Commands {
    Print(PrintArgs),
    Play(PlayArgs),
}

#[derive(MergeConfig)]
#[merge_config(app_name = "my-app")]
pub struct Config {
    #[merge_config(common)]
    pub log_level: LogLevel,
    #[merge_config(common)]
    pub log_format: LogFormat,

    #[merge_config(default = "\"World\".to_string()")]
    pub name: String,

    #[merge_config(subcommand)]
    pub command: Commands,
}
#+end_src

The user function then matches on ~config.command~:

#+begin_src rustic :results none :exports code
#[foundation_main]
pub fn main(config: Config) -> Result<ExitCode, AppError> {
    match config.command {
        Commands::Print(args) => println!("{}", args.message),
        Commands::Play(args) => play(&args.track),
    }
    Ok(ExitCode::SUCCESS)
}
#+end_src

*** Limitations

Subcommand fields are *CLI-only*.  They are deliberately omitted from
~ConfigFileRaw~ — TOML has no clean tagged-enum mapping for clap-style
subcommands, and "default subcommand pinned by config file" is not a goal
of this macro.  Per-variant arg defaults from the config file remain a
possible future addition; today, projects that want such defaults should
layer them in the variant's own ~Args~ struct or via a wrapper script.

The ~subcommand~ kind rejects ~default~, ~required~, ~env~, ~short~,
~parse~, ~cli_only~, and ~name~.  Those attributes have no meaning for a
passthrough field — the macro errors at compile time if any are present.

At most one ~subcommand~ field is permitted per struct.

** Extension points: ~extra_cli~, ~extra_file~, ~extra_error~

The struct-level ~merge_config~ attribute accepts three optional paths
that let a project widen the macro's surface without forking it.  Each
takes a string-quoted Rust path:

#+begin_src rustic :results none :exports code
#[derive(MergeConfig)]
#[merge_config(
    app_name = "my-app",
    extra_cli = "MyCliArgs",
    extra_file = "MyFileArgs",
    extra_error = "crate::MyError",
)]
pub struct Config { /* … */ }
#+end_src

*** ~extra_cli = "Type"~

Flattens ~Type~ (a ~clap::Args~ struct) into the generated ~CliRaw~ via
~#[command(flatten)]~.  Use this for groups of CLI-only arguments that
do not belong on the merged ~Config~ — typically the inputs to a ~skip~
field's ~resolve_<field>~ method.

The flattened struct appears as ~cli.extra~ inside resolvers.

*** ~extra_file = "Type"~

Flattens ~Type~ (a ~serde::Deserialize~ struct) into the generated
~ConfigFileRaw~ via ~#[serde(flatten)]~.  Companion to ~extra_cli~ for
inputs that also need a config-file source.

The flattened struct appears as ~file.extra~ inside resolvers.

*** ~extra_error = "Type"~

Adds an ~Extra(Type)~ variant to the generated ~ConfigError~ with
~#[error(transparent)]~ and ~impl From<Type> for ConfigError~.  Without
this, the only escape hatch for resolver failures is
~ConfigError::Validation(String)~ — a flattened message that loses any
structure the original error carried.  ~extra_error~ preserves the
caller's error type intact, so ~Display~ output is unchanged and
downstream code can still match on the original variants.

A ~resolve_<field>~ method can then return ~Result<T, MyError>~
directly, and the ~?~ inside the macro-generated ~from_cli_and_file~
will convert it via the auto-generated ~From~:

#+begin_src rustic :results none :exports code
#[derive(thiserror::Error, Debug)]
pub enum MyError {
    #[error("widget catalogue is empty")]
    EmptyCatalogue,
}

#[derive(MergeConfig)]
#[merge_config(
    app_name = "my-app",
    extra_error = "crate::MyError",
)]
pub struct Config {
    #[merge_config(common)] pub log_level: LogLevel,
    #[merge_config(common)] pub log_format: LogFormat,
    #[merge_config(skip)]   pub catalogue: Catalogue,
}

impl Config {
    fn resolve_catalogue(
        _cli: &CliRaw,
        _file: &ConfigFileRaw,
    ) -> Result<Catalogue, MyError> {
        Err(MyError::EmptyCatalogue)
    }
}
#+end_src

Callers that need to discriminate get ~ConfigError::Extra(MyError::…)~
back; callers that only print the error see the inner ~Display~
verbatim, with no extra wrapper text.

* Environment variables

** Naming scheme

Every env-var name read by an app generated through ~MergeConfig~ is
*lowercase*, with the app name as a prefix and underscores between
words: ~<app>_<flag>~.  Hyphens in the app name become underscores
(POSIX env-var names are restricted to letters, digits, and
underscore).

Concrete examples for ~app_name = "example-server"~:

| Field / flag    | Env var                       |
|-----------------+-------------------------------|
| ~--log-level~   | ~example_server_log_level~    |
| ~--log-format~  | ~example_server_log_format~   |
| ~--config~      | ~example_server_config~       |
| ~--listen~      | ~example_server_listen~       |
| ~--base-url~    | ~example_server_base_url~     |

** Why lowercase?  POSIX §8.1

The convention many projects reach for —
~APP_THING_IN_SHOUTING_CASE~ — is the convention POSIX defines for
its /own/ utility variables (~PATH~, ~HOME~, ~LANG~, …), not for
application variables.  The relevant standard is IEEE Std 1003.1-2017
(POSIX.1-2017), [[https://pubs.opengroup.org/onlinepubs/9699919799/basedefs/V1_chap08.html][Chapter 8 — Environment Variables]].

§8.1 states (verbatim):

#+begin_quote
Environment variable names used by the utilities in the Shell and
Utilities volume of POSIX.1-2017 consist solely of uppercase letters,
digits, and the <underscore> ( '_' ) from the characters defined in
Portable Character Set and do not begin with a digit.
#+end_quote

and immediately after:

#+begin_quote
The name space of environment variable names containing lowercase
letters is reserved for applications.  Applications can define any
environment variables with names from this name space without
modifying the behavior of the standard utilities.
#+end_quote

The standard distinguishes /Standard Utilities/ from /Applications/.
[[https://pubs.opengroup.org/onlinepubs/9699919799/basedefs/V1_chap03.html][Chapter 3 — Definitions]] gives:

- *§3.17 Application:* "A computer program that performs some desired
  function."
- *§3.369 Standard Utilities:* "The utilities described in the Shell
  and Utilities volume of POSIX.1-2017."

Anything any of us writes is an /Application/ by §3.17 — utilities are
the specific programs the standard itself describes.  So the
namespace explicitly carved out for /our/ env vars is the one
containing lowercase letters.  Using lowercase is what the standard
asks for and is guaranteed not to collide with current or future
POSIX utility variables.

The widespread instinct to write ~APP_FOO~ for application variables
is a cargo-culted carry-over from the §8.1 utility rule.  It is not
required by any tool in a normal Unix deployment path — POSIX shells
(bash, zsh, dash), systemd ~Environment=~, Docker ~ENV~, Kubernetes
env, clap's ~env = "..."~, and CI runners (GitHub Actions, GitLab CI)
all preserve case and treat the name verbatim.

** Why prefix?

POSIX does not mandate a prefix, but it does warn that the lowercase
namespace is shared across all applications on the system.  A bare
name like ~listen~ or ~base_url~ is liable to collide with another
process's variables or with a developer's shell environment, and
~LISTEN~ specifically lives near systemd's ~LISTEN_FDS~ /
~LISTEN_PID~ socket-activation contract.  Prefixing with the app name
sidesteps both.

** ~env~ vs ~env = "literal"~

The ~MergeConfig~ derive accepts two forms of the ~env~ attribute on
merged fields:

- *Bare ~env~* — derive the name as ~<app>_<flag>~, where ~flag~ is
  the ~name = "..."~ override if present, otherwise the field
  identifier.  Use this whenever the derivation gives the right
  answer.

  #+begin_src rustic :results none :exports code
  #[merge_config(env, required)]
  pub base_url: String,
  // → reads `<app>_base_url`
  #+end_src

- *~env = "literal"~* — use the literal verbatim, with no prefixing.
  Reserved for genuine deviations: a name imposed by an external
  contract, or the rare case where the derived form is wrong.  When
  you reach for the literal form, leave a comment beside it that
  explains *why* it deviates — the explicit form is now the
  attention-getter, so it should earn the attention.

  #+begin_src rustic :results none :exports code
  // External: matches the legacy `MYORG_LICENCE_KEY` contract used
  // by every other tool in the suite; do not rename without updating
  // those callers.
  #[merge_config(env = "MYORG_LICENCE_KEY", required)]
  pub licence_key: String,
  #+end_src

Omit the attribute entirely on fields that should *not* read from the
environment (subcommand selectors, secrets you want to source only
from a credential file, etc.).

** Consequences for tooling

A field's env-var name is no longer a literal string in the source —
it is derived at macro expansion.  Two ways to recover the spelling:

- Run the binary with ~--help~.  Clap prints each flag's env-var name
  in the right-hand column ("[env: ~my_app_listen~]"), so a user
  trying to find the right variable to set has the answer in front of
  them with no source dive.
- ~cargo expand~ shows the expanded ~CliRaw~ if you need to confirm
  exactly what clap sees, or want to grep the post-expansion form.

When grepping the source itself, search by the field name (or, for a
~name~ override, by the override) rather than by the env-var
spelling.

* Systemd integration

Foundation provides built-in systemd integration:

- *~notify_ready()~* — sends ~READY=1~ to systemd when the server is listening.
- *~spawn_watchdog()~* — sends heartbeats at half the configured
  ~WATCHDOG_USEC~ interval.
- *Socket activation* — ~tokio-listener~ supports ~sd-listen~ for inheriting
  sockets from systemd.
- *Credential loading* — ~credential_secret_path()~ reads OIDC client secrets
  from systemd's ~CREDENTIALS_DIRECTORY~.

* Multiple servers

For multiple servers (e.g. primary + admin), return multiple configs and receive
a tuple:

#+begin_src rustic :results none :exports code
impl ServerApp for Config {
    fn server_run_configs(&self) -> Vec<ServerRunConfig> {
        vec![self.primary_config(), self.admin_config()]
    }
}

#[foundation_main]
pub async fn main(
    config: Config,
    (primary, admin): (Server, Server),
) -> Result<ExitCode, AppError> {
    tokio::select! {
        r = primary.listen() => r?,
        r = admin.listen() => r?,
    }
    Ok(ExitCode::SUCCESS)
}
#+end_src

For fully dynamic cases, create additional servers at runtime:

#+begin_src rustic :results none :exports code
let extra = Server::new(server.base_state().clone(), extra_config);
#+end_src

* Lifecycle hooks

| Stage                      | Hook                              | Example use                                   |
|----------------------------+-----------------------------------+-----------------------------------------------|
| CLI parsing                | ~CliApp::from_cli()~              | Custom validation, env var fallbacks           |
| Config → ServerRunConfig   | ~ServerApp::server_run_configs()~ | Control listen addr, OIDC, frontend path       |
| State construction         | ~Server::with_state(\vert{}base\vert{} ...)~ | Add app-specific fields, custom metrics        |
| Route registration         | ~Server::api_route()~ / ~merge()~ | All app-specific routes                        |
| Additional servers         | ~Server::new(base.clone(), cfg)~  | Admin API on separate port                     |
| Post-listen cleanup        | Code after ~server.listen().await~ | Drain queues, close connections                |

Every hook has a sensible default.  Touch only the hooks you need.

* Service helpers (Nix)

The ~mkNixosService~ and ~mkDarwinService~ flake helpers each emit a
single module under ~services.<name>~.  They are designed to be
/composed with/, not /forked from/ — spawned projects extend them by
declaring additional options or overriding existing module values from
a second module imported alongside.  No ~extraOptions~ parameter
exists or is needed: the Nix module system's own merging is the
extension point.

The thin wrapper at ~nix/modules/nixos-server.nix~ (and its Darwin
counterpart) is the natural place to add project-specific extensions.
By default it forwards to the helper; turning it into a module
function that imports the helper /and/ contributes its own options and
config gives full composition with no additional plumbing.

Every value the helpers set on ~serviceConfig~ / ~socketConfig~ /
~launchd.servers.<name>.serviceConfig~ is wrapped in ~lib.mkDefault~,
so plain assignment from a downstream module overrides cleanly.
~lib.mkForce~ is needed only when overriding something the helper sets
without ~mkDefault~ — typically lists like ~wantedBy~, ~after~, and
~requires~, which the module system merges by concatenation anyway and
so rarely benefit from a forced replacement.

** Example: inject a generated TOML config file

A common need is to render a configuration file from a Nix attribute
and pass its path to the server via ~--config~.  After ~mkDefault~
wrapping, plain assignment overrides the helper's ~ExecStart~ — no
~mkForce~ required.

#+begin_src nix :results none :exports code
{
  self,
  foundation,
}: {
  config,
  lib,
  pkgs,
  ...
}: let
  cfg = config.services.rust-template-server;
  rulesFile = (pkgs.formats.toml {}).generate "rules.toml" {
    rules = cfg.rules;
  };
in {
  imports = [
    (foundation.lib.mkNixosService {
      name = "rust-template-server";
      inherit self;
    })
  ];

  options.services.rust-template-server.rules = lib.mkOption {
    type = lib.types.attrsOf lib.types.str;
    default = {};
    description = "Routing rules read by the server at startup.";
  };

  config = lib.mkIf cfg.enable {
    systemd.services.rust-template-server.serviceConfig.ExecStart =
      "${cfg.package}/bin/rust-template-server"
      + (
        if cfg.socket != null
        then " --listen sd-listen"
        else " --listen ${cfg.host}:${toString cfg.port}"
      )
      + " --frontend-path ${cfg.frontendPath}"
      + " --config ${rulesFile}";
  };
}
#+end_src

** Lighter alternative: extend the environment

Where the binary can read configuration through an environment
variable, the override does not need to touch ~ExecStart~ at all — set
the variable directly under the merged ~services.<name>~ environment.
The helper applies ~mkDefault~ per key, so contributing a new key is
pure addition with no override:
